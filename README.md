# LivePhoto 浏览器

### Windows 上最好用的 iPhone Live Photo 浏览器

滚一下就到，点一下就活，有声音。

Windows 自带的「照片」把一张 Live Photo 显示成静止的 HEIC，资源管理器把 `IMG_1234.HEIC`
和 `IMG_1234.MOV` 摆成两个互不相干的文件。Live Photo 之所以叫 Live，是因为按下它的
那一刻照片会动。

这个工具只做一件事：**在 Windows 上把 iPhone 导出的 Live Photo 正确、流畅、好看地放出来。**

---

## 它有什么

### 📸 像一个正经相册

- 选一个文件夹，就等于打开一个相册；关掉就走，照片留在原地，一张都不复制
- 17,159 个文件的目录 **257 ms** 扫完（66,769 文件/秒）
- 左侧目录树（按子树计数、点击过滤）、日期分组、右侧月份时间轴

索引阶段只读目录项、不打开文件内容，所以 iCloud / OneDrive 里那些数据不在本地的
云端占位文件不会触发下载 —— 整个库都在云上，网格也照样秒开。

### 🎞️ Live Photo 保持 Live

| 能力 | 做法 |
|---|---|
| **网格悬停即预览** | 鼠标停 0.4 秒，那一格静音循环动起来；滚走就停 |
| **点一下播放** | 全屏里点 `LIVE ▶` 或按 **空格**，带声音播一遍 |
| **切过去自动播放** | 滑到一张 Live Photo 就自动播，和 iOS 相册一样 |
| **零转码** | 系统 HEVC 扩展解出的原始 MOV 直接交给播放器，转码和预览缓存都省掉 |
| **配对准确** | 同目录同名主干配对，真实库 311 对全部命中 |

### ⚡ 快，每一格都有实测数字

| 环节 | 实测 |
|---|---|
| 扫描 17,159 个文件 | **257 ms** |
| 已缓存缩略图读取 | **14,896 张/秒** |
| 网格滚动（5000 格、真实照片） | **58.5 fps**，p50 = **16.7 ms**，跑满 60 Hz vsync |
| 7832 个资产同时存在时的 DOM 节点 | **54 个** |
| 全屏切换（已预加载） | p50 **35 ms** |
| 打开一个 2.08 GB 的 4K 视频 | **274 ms** 起播，界面停顿 **0 ms**，内存峰值 **28 MB** |

快来自四处设计选择：

1. **索引只碰元数据**：只读目录项，从不打开文件内容 —— 这同时保证了云端库也能秒开。
2. **只解你正在看的那一屏**：滚过即取消。清空缓存后打开一个大目录，只生成 111 张缩略图
   （正好可见区）就停下，其余 7800 多个资产一个都没碰。
3. **多级图源，等待消失在界面里**：网格层立刻顶上，全屏层算好无缝替换；
   预加载过的图直接显示清晰图。
4. **缓存是纯派生数据**：存在 `%LOCALAPPDATA%\LivePhoto\cache`，4 GB 上限、最旧优先淘汰；
   整个删掉只损失一点时间，照片文件一个字节都不动。

### 🛡️ 几个 GB 的视频照样能播

手机导出的视频常有几个 GB。本机库里有一个 **2.08 GB / 4K / 325 秒** 的片子，实测：
`canplay` **274 ms**、界面停顿 **0 ms**、宿主进程内存峰值 **28 MB**、协议实际传输 **28.6 MB**
—— 播放器开始播放需要的只是文件头加起始样本。

16 个最大的视频（最大 2.08 GB）连续测试：**16/16 正常播放，0 失败，最差界面停顿 0 ms**。

做法三条：自定义协议按 **4 MB 分片**响应（HTTP Range）；读盘放在独立的 IO 线程池，
界面线程专心做 UI；播放请求在 IO 池里优先于缩略图请求。

| 操作 | 作用 |
|---|---|

## 下载与运行

去 [Releases](../../releases) 下载 `LivePhotoBrowser.exe`，**双击即用**：

- 单文件 **4.6 MB**，免安装，不依赖 Node 或 Vite
- 打开后填文件夹路径，或设环境变量 `LIVEPHOTO_OPEN` 直接进入

```powershell
$env:LIVEPHOTO_OPEN="F:\DCIM"; .\LivePhotoBrowser.exe
```

### 环境要求

- Windows 10 1809+ / Windows 11
- **WebView2 运行时**（Windows 11 已内置）
- **HEIC / HEVC 解码**：微软的 *HEIF 图像扩展* 与 *HEVC 视频扩展*。
  多数品牌机预装；装上之后 HEIC 缩略图与 Live Photo 播放都可用。

## 自己构建

```powershell
cd app; pnpm install; pnpm build                      # 前端 → app/dist
cd ..; cargo build --release -p app --features custom-protocol
# 产物：target/release/app.exe（约 4.6 MB）
```

> ⚠️ **`--features custom-protocol` 必须带。**
> `tauri` 的 build.rs 用 `let dev = !custom_protocol;` 判断 dev/prod ——
> 缺了它，release 二进制会去连 `devUrl`（localhost:1420），窗口白屏且没有任何报错。
> 用官方 CLI（`pnpm tauri build`）会自动带上。

开发模式（debug 加载 `devUrl`，需要同时起 Vite）：

```powershell
cd app; pnpm dev                       # 终端 1
$env:LIVEPHOTO_OPEN="F:\DCIM"; .\target\debug\app.exe   # 终端 2
```

### 构建产物体积（实测）

运行需要的只有 `LivePhotoBrowser.exe` 一个文件。`target/` 是编译器的中间缓存，
删掉之后程序照跑，下次构建重新生成。它的真实量级：

| 状态 | `target/` | 文件数 | 冷构建耗时 |
|---|---|---|---|
| 干净构建（快档 `LTO=false`，246 个 crate） | **1.77 GB** | 3,679 | **14 分 11 秒** |
| 再删掉 `*.pdb`（只有调试器要用） | **1.52 GB** | 3,569 | — |
| 混用不同 profile 设置反复构建 | 3.94 GB | 8,421 | — |

表格第三行是一个真实踩过的坑：每次改 `CARGO_PROFILE_RELEASE_LTO` / `OPT_LEVEL` 这类覆盖，
crate 的 hash 就会变，同一批依赖被再编一份，旧的那份留在 `target/deps` 里。
实测堆到 775 个 `.rlib`（干净构建 360 个），多出 2.4 GB。统一使用 `Cargo.toml` 里的
profile，或换设置前先 `cargo clean`，体积就一直是干净构建的水平。

### 图标

`python tools/gen-icon.py` 用 Pillow 生成 **9 个尺寸**（16–256）的 `icon.ico` 和各尺寸 png：
圆角方块配蓝→青渐变，白色播放三角表示"会播放"，左上角两个同心圆环加中心点
是 iOS 实况照片的记号。多尺寸是必要的 —— Windows 在任务栏、标题栏、Alt-Tab、
资源管理器大图标处各用不同尺寸，塞一张大图让系统缩，小尺寸会糊。

改完图标后顺手碰一下 `app/src-tauri/tauri.conf.json` 再构建：
`tauri-build` 的 `rerun-if-changed` 只列了这个配置文件，不含图标文件
（细节见 `docs/实施记录.md` 的 K18）。

## 技术栈与结构

**Rust 核心 + Tauri v2 + WebView2**。程序本身不打包 Chromium，也不打包编解码器 ——
HEIC 与 HEVC 全部走系统扩展，可执行文件因此只有 4.6 MB。

```
core/                 # 核心层，不依赖 Tauri（所以 bench 能秒级编译）
  files.rs            # 目录扫描：只读元数据 + 云占位识别
  pairing.rs          # Live Photo 三级配对
  movmeta.rs          # MOV box 解析：时长/编码/分辨率/still-image-time
  cache.rs            # 磁盘缓存 + LRU 淘汰
  thumbs.rs           # 缩略图工作池：常驻 STA 线程 + 优先级队列
  media/wic.rs        # WIC 图片解码
  media/mf.rs         # Media Foundation 视频抽帧
  src/bin/            # 各类 bench 与验收工具（所有性能结论都可复跑）
app/                  # Tauri 应用：命令层 + 自定义协议 + 前端
docs/                 # 三份文档，分工明确
tools/                # 侦察/验证脚本 + 图标生成
```

## 现在的边界

1. **首次浏览大库时缩略图逐个填充**：HEIC 解码约 900 ms/张，系统解码器几乎不能并行
   （6 线程只有 1.4× 加速）。浏览过程不被阻塞，填过一次就永久命中缓存。
2. **全屏翻页上限约 2~4.7 张/秒**：翻得更快时，底部胶片条会显示"正在准备"。
3. **日期取文件修改时间**，目前还没读 EXIF 拍摄时间。
4. **滚轮由前端接管**，因此没有原生惯性。
5. **只读浏览**，v1 没有编辑与导出。
6. **交付形式是绿色单文件**，安装包（MSI/NSIS）还没做。
7. **一次没能彻底归因的偶发**：首屏正在加载时出现过 1 次"播放 6 秒未就绪"
   （同一份文件在安静时 274 ms 就绪）。已经把播放请求提到 IO 池优先、读盘移出界面线程，
   连测 4 次全部通过；这次失败原样记录在 `docs/实施记录.md` 的 D24。
