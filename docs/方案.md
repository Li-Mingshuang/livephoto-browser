# LivePhoto 浏览器 for Windows —— 技术方案 v1

> 目标：Windows 上轻量、流畅地浏览 iPhone 导出的 Live Photo，体验对齐 Apple 相册；架构上为「未来用模型给照片分类」预留好位置。
>
> 本文所有性能数字与格式结论，均来自**本机真实相册实测**（脚本见 `tools/`），不是估算。

---

## 0. 结论先行

| 决策项 | 结论 | 理由（一句话） |
|---|---|---|
| 技术栈 | **Rust 核心 + Tauri v2（WebView2 渲染 UI）** | 安装包 ~10MB、不打包 Chromium；重活（解码/缓存/索引/推理）全在 Rust；UI 质感用 CSS 做，成本最低 |
| HEIC 解码 | **Windows WIC HEIF 解码器为主，libheif 为备** | 免打包、走系统 HEIF 扩展；本机 `Microsoft.HEIFImageExtension 1.2.48.0` 已装 |
| HEVC 解码 | **Media Foundation（硬件解码）为主，FFmpeg 插件为备** | 本机 `Microsoft.HEVCVideoExtension 2.4.109.0` 已装；零打包体积 |
| 首屏策略 | **两级缓存 + 后台渐进升级** | 实测 12MP HEIC 全解码 p50=417ms，1 万张要 ~9 分钟，绝不能在首屏做 |
| 配对策略 | **同目录同名 stem 为主（实测覆盖 100%），content-identifier 为辅** | 实测 311 对全部靠同名 stem 命中，且本机 HEIC 里**没有** ContentIdentifier |
| 云端占位 | **必须一等公民支持** | 本机 iCloud 相册 663 个文件全是未下载占位，直接读会失败 |
| 列表渲染 | 虚拟化网格 + GPU 图集（atlas） | 支撑 10 万张照片 120Hz 滚动 |
| AI 分类 | 缩略图管线 → ONNX Runtime(DirectML) → 向量 + 标签，模型按需下载 | 复用已解码的 224px 缩略图，推理不额外解码 |

**最需要你拍板的一件事**：栈选「Tauri（UI 开发快、体积小但内存 ~200MB）」还是「纯 Rust + wgpu 自绘（内存 ~80MB、单 exe，但 UI 工量大 3-5 倍）」。见 §6。

## 0.5 M0 实测修正（2026-09-13）

M0 技术验证已跑完 3/4 项，**有两处结论需要用实测数据修正本方案**。
完整数据与复现方式见 `M0-实测发现.md`。

| 原方案假设 | 实测 | 修正 |
|---|---|---|
| 12MP HEIC 解码 ≈417ms/张，8 线并行 → 1 万张约 9 分钟 | 实际 **435–463ms/张**，但 **6 线程只提速 1.4×** → 1 万张 **55 分钟** | **首屏体验方案不变（缓存+渐进+可见优先），但"首次全库索引"要按小时级设计**：必须可断点续传、可后台闲时跑、有进度与暂停；并把"Live Photo 海报帧优先从 MOV 取"从优化项升级为**必做项** |
| 假定线性并行，缓存与工作池按"吞吐"设计 | 6 线程 1.4×、6 进程 2.0×、单张 CPU 时间只占墙钟 53%（一半在阻塞等待） | 瓶颈是**同步等待**而非 CPU 算力，加线程/加进程都无效。M1 之前必须先查清串行化来源，否则工作量估算全是错的 |
| MF 抽帧应该是毫秒级（硬解） | 抽单帧 **≈200ms**（且缩到 256px 只快 18%），整段解码仅 **24.7 fps**@1440p | ≈200ms 是 **每个 SourceReader 的一次性建链开销**，不是像素工作量 → 必须**复用常驻 SourceReader**；同时"是否真吃了硬解"待查 |
| WebView2 网格能否撑住 10 万张存疑 | 5000 格 **58.5fps 跑满 60Hz vsync**，p99 33.5ms，DOM 仅 88 节点，长任务 0 | ✅ **UI 栈选型得到实测支持**，可放心推进 M1–M3 |

**M0 还未完成**：H.264 预览片段转码（SRS-3）、SourceReader 复用后的抽帧速度、120Hz 验证（本机非 120Hz 屏）。

**新增的硬约束（已在代码里落实）**：
- HEIC 解码**必须**在 STA 套间（MTA 会永久死锁）；每线程独立 STA + 独立 WIC 工厂。
- `MFStartup` 必须调（对 HEIC 解码有 2 倍收益）。
- **Tauri 主线程绝不能初始化 MTA COM**（会让 tao 的 `OleInitialize` panic）。
- JPEG 路径必须让 WIC 输出 `24bppRGB`（`image` 的 JPEG 编码器不接受 RGBA8）。

## 1. 实测发现（本机真实数据）

侦察环境：Windows 11 (10.0.22631)，8 核，已装 HEIF/HEVC/WebP/AV1 扩展、iCloud for Windows、Python 3.12（含 pillow 11.3 + pillow_heif 1.0）。

### 1.1 找到了两个性质完全不同的"相册"

| 位置 | 文件数 | 性质 | 能否读取 |
|---|---|---|---|
| `C:\Users\lms\Pictures\iCloud Photos\Photos` | 666（合计 1.38GB） | **iCloud 云端占位文件** | ❌ 读不了 |
| `F:\DCIM\**` | 17,159 | 真实本地库（含 iPhone 导出 Live Photo） | ✅ |

**iCloud 目录的坑（必须处理）**：

```
属性 = 4199968 = 0x401620
     = FILE_ATTRIBUTE_ARCHIVE(0x20)
     | SPARSE_FILE(0x200)
     | REPARSE_POINT(0x400)
     | OFFLINE(0x1000)
     | RECALL_ON_DATA_ACCESS(0x400000)
```

664/666 个文件是这种"数据在云上、本地只有占位"的状态，而且本机 **iCloud 客户端进程当前没在跑**，所以读取直接抛：

```
OSError: [Errno 22] Invalid argument      ← 底层 HRESULT 0x8007018B
The cloud file provider is not running.
```

> 这意味着：**任何"打开文件读字节"的操作都必须假设它会失败**。打开目录列文件名是可以的（元数据在本地），一旦碰内容就可能是"触发下载"或"直接报错"。方案的 §5 专门讲这个。

### 1.2 Live Photo 的真实配对规律（F:\DCIM 实测）

```
scanned: 17,159  扩展名分布:
  jpg 6409 · nef 6430 · nksc 1618 · xmp 952 · heic 734 · mov 597
  mp4 321 · png 38 · tif 31 · jpeg 13 · zip 6 · db 4 · jfif 1

按「同目录 + 同名 stem」配对:  命中 311 对
  .heic + .mov  → 278
  .jpg  + .mov  →  20
  .jpeg + .mov  →  13
未被命中（孤儿）: 607 个视频
```

样例（注意用户的文件被重命名过，加了时间戳前缀，但**两半前缀一致**）：

```
2025_05_06_19_43_IMG_9032.HEIC  +  2025_05_06_19_43_IMG_9032.MOV
2025_05_06_19_43_IMG_9031.HEIC  +  2025_05_06_19_43_IMG_9031.MOV
```

**结论 1：配对的主键是 `目录 + 文件名主干`，与扩展名大小写无关。** 这对 iPhone→Windows 的所有导出方式（iCloud for Windows、Image Capture、文件 App 拷贝）都成立，因为两半天生同名。

**结论 2（反直觉，很重要）：本机 HEIC 里没有 ContentIdentifier。** 抽 40 张 HEIC 全文件扫字节，`ContentIdentifier` 命中 0。所以**不能**把 Apple 的 content-identifier 当作主配对策略，只能当第三级兜底。

**结论 3：607 个孤儿视频要区分两类。** 用「MOV 里有没有 still-image-time 元数据」判定它是 Live Photo 视频还是普通录像 —— 抽 40 个视频，38 个都带 `com.apple.quicktime.still-image-time`。孤儿 Live Photo 视频（剧照那半丢了）应该显示为"可播放的视频"，海报帧从 MOV 自己抽。

### 1.3 Live Photo 的 MOV 内部结构（box 级解析）

```
file: 2025_05_06_19_43_IMG_9032.MOV     3.53 MB
  duration_s  : 1.94        （三个样本 1.94 / 2.67 / 1.82 —— 不是固定的 3 秒）
  timescale   : 600
  handlers    : vide, soun, meta, … + alis（别名轨道）
  video track : hvc1  1920x1440
  audio track : lpcm
  metadata    : com.apple.quicktime.still-image-time          ✅
                com.apple.quicktime.content.identifier          ✅
                com.apple.quicktime.live-photo-info             ✅
                com.apple.quicktime.live-photo.vitality-score   ✅  ← Apple 用来挑"关键帧"的分数
                …vitality-scoring-version                       ✅
```

**这五个结论直接决定播放器设计：**

1. **视频编码是 HEVC（`hvc1`），必须能解 HEVC** —— 没有纯软件兜底就没有播放能力。
2. **分辨率 1920×1440，2 秒左右** —— 体量小，可以整段解码、也可以做预览转码，都很便宜。
3. **有独立音轨（lpcm）** —— 播放必须处理音视频同步和静音开关。
4. **`still-image-time` 给出"剧照在视频里的时刻"** —— 按住播放时，要让视频从剧照那一帧对齐开始播，才能有 Apple 那种"照片活过来"的感觉。
5. **`vitality-score`** —— Apple 自己给段内各帧打的分，可以作为"选哪一帧当封面"的依据。

### 1.4 性能基线（决定缓存架构的关键数字）

```
24 个 iPhone HEIC (4032x3024, 12MP)，8 核:

  HEIC 全量解码           p50 = 417 ms   p90 = 553 ms   min 284 / max 599
  解码 + 缩到 512px + 编码 p50 = 121 ms
  （Pillow/PIL 软件路径，libde265 逐图单线程）

  推算：1 万张 HEIC × 417ms ÷ 8 并行 ≈ 520 秒 ≈ 9 分钟
```

**结论 4：首屏绝对不能等解码。** 必须做到：
- 首屏只用"文件名 + 目录元数据"渲染网格骨架（毫秒级）；
- 缩略图由后台工作池渐进填充，用户滚动到哪先算哪（可见优先队列）；
- 结果全部落盘缓存，二次启动直接命中；
- 用户能看到"正在处理 N 个项目"的进度（这正是 Apple 相册首次导入时的行为，体验上是一致的，不算妥协）。

**结论 5：内嵌缩略图这条路在 iPhone HEIC 上走不通。**
`pillow_heif` 报告 `thumbnails: 0` —— iPhone HEIC **没有**可用的内嵌缩略图（只有 `aux`/`depth_images` 辅助图，不是缩略图）。所以没有"零成本拿小图"的捷径，只能靠并行解码 + 缓存。这也进一步说明 **Live Photo 的封面帧优先从 MOV 取**（HEVC 硬解 1920×1440 只要几毫秒，比 HEIC 快 1~2 个数量级）是一个很划算的优化。

### 1.5 本机可用的系统能力

| 能力 | 状态 | 对方案的意义 |
|---|---|---|
| `Microsoft.HEIFImageExtension` 1.2.48.0 | ✅ 已装 | WIC 可直接解 HEIC，不必打包 libheif |
| `Microsoft.HEVCVideoExtension` 2.4.109.0 | ✅ 已装 | MF 可硬解 hvc1，不必打包 FFmpeg |
| `Microsoft.WebpImageExtension` / `VP9` / `AV1` | ✅ 已装 | 缓存格式可自由选 |
| .NET | 只有 runtime，**没有 SDK** | 排除 WinUI/WPF 路线（要先装几个 G） |
| Rust / cargo | ❌ 未安装 | 需要 `rustup` + MSVC Build Tools（约 1-2GB，一次性） |
| Python 3.12 + pillow_heif | ✅ | 仅用于工具/验证脚本，不做产品运行时 |

## 2. 产品定义：什么叫"达到苹果相册的体验"

### 2.0 产品形态（理想形态）

一句话：**它不是"照片管理器"，是一个"文件夹浏览器"。**

打开它 → 左边是这次打开的目录树 → 右边立刻是一屏照片 → 滚轮往下滚就是
时间轴 → Ctrl+滚轮调缩略图大小 → 双击一张照片进入全屏 → 在 Live Photo 上按住，
照片就活过来、会动会出声。

形态上刻意守住四条：

1. **没有"库"这个概念，只有"这次打开的文件夹"。**
   不导入、不建库、不索引到数据库、不复制任何文件。文件夹就是库，
   所以"打开"这个动作的代价只有扫描元数据（17k 文件 257ms），
   而不是"等待导入完成"。关掉再打开，还是同一个文件夹。
2. **照片永远比界面先到。** 任何需要等待解码的地方，都是先用已有的低清图顶上，
   同时后台算高清、算好了无缝替换。用户永远看不到空白与转圈。
3. **只加工"正在看的东西"。** 不解你看不到的图、不算你没打开过的目录。
   资源分配的原则是"可见优先"，而不是"先把全库处理完再给你看"。
4. **克制。** 没有编辑、没有云、没有社交、没有回忆成片。
   它只做一件事：把 iPhone 导出的 Live Photo 好看、流畅、正确地放出来。

完整的目标交互清单见 §2.1，明确不做的事见 §2.2。

把"感觉"翻译成可验收的行为清单。每一条都是能测的。

### 2.1 核心交互（v1 必须做到）

| # | 行为 | 验收标准 |
|---|---|---|
| 1 | 打开即见网格 | 冷启动到首屏可见 ≤ 800ms（有缓存）/ ≤ 1.5s（无缓存，先出骨架） |
| 2 | 滚动如丝 | 10 万张库内滚动稳定 60fps，120Hz 屏上稳定 120fps；主线程单帧 >8ms 的卡顿 0 次 |
| 3 | Live Photo 一眼可辨 | 网格里带 `LIVE` 角标；鼠标悬停 ~400ms 自动**静音循环**播放（对齐 iOS 网格的长按预览 / Apple 的 hover 预览） |
| 4 | 按住/点击播放 | 全屏中按住空格或点击 `LIVE` 按钮 → 从**剧照那一帧**开始带动画+声音播放，松手回到剧照；起播延迟 ≤ 100ms |
| 5 | 大图秒开 | 点开一张 → 先显示缓存的中图并**立即**开始按需解全图，≤ 200ms 内看到清晰图（而不是转圈） |
| 6 | 缩放平移 | 滚轮/触控板缩放、拖拽平移、双击回中；缩放过程 60fps（用纹理缩放，不重新解码） |
| 7 | 键盘流 | ←/→ 切换、空格播放、Esc 退出、+/- 缩放、F 收藏、数字键打星 |
| 8 | 网格↔全屏转场 | 从被点的那一格"长"成全屏（hero transition），带缓动，≤ 250ms |
| 9 | 信息面板 | 拍摄时间、机型、镜头、光圈/快门/ISO、GPS、文件路径、体积、是否 Live |
| 10 | 深浅色 | 跟随系统，Apple 风的半透明侧栏/工具栏（`backdrop-filter`） |
| 11 | 中文本地化 | 界面全中文，日期用 `2025年5月6日 19:43` 这类格式 |
| 12 | 收藏/隐藏 | 收藏写入本地库（**不修改原文件**，避免污染用户资料） |

### 2.2 明确不做（v1 non-goals）

- ❌ 不做照片编辑（裁剪/滤镜/调色）
- ❌ 不做云同步、账号、上传
- ❌ 不改动/移动/删除用户原始文件（只读；"导出/另存为"是唯一的写操作）
- ❌ 不做 iOS 那种"回忆/Memories"自动成片（M7 之后再看）
- ❌ 不支持 RAW 显影（NEF 只读内嵌 JPEG 预览，够看不够修）

## 3. 数据与配对设计

### 3.1 配对引擎（三级策略）

```
输入：一次目录扫描得到的文件列表
输出：Asset 列表（每个 Asset 可能是 still / live / video / raw）

第 1 级 · 同目录同名主干（覆盖率实测 100%，最快）
  key = (lower(目录), lower(文件名主干))
  主干下有 {.heic/.heif/.jpg/.jpeg/.png} 且同时有 {.mov/.mp4} → live
  主干下只有照片 → still
  主干下只有视频 → video（候选：可能是光子丢了，见第 3 级）

第 2 级 · 元数据锚定
  读 MOV 头部 box：
    - 有 com.apple.quicktime.content.identifier
      → 在同一个目录里找带相同 identifier 的 still（覆盖率低，但 AirDrop/macOS 导出会遇到）
    - 有 com.apple.quicktime.still-image-time
      → 确认这是"Live Photo 视频"，即使没有剧照也按 live 视频展示（海报从视频抽帧）

第 3 级 · 时空邻近兜底（仅对第 1、2 级都没配上的孤儿）
  条件同时满足才配对，且置信度标注为 low：
    - 同一目录
    - MOV 带 still-image-time 元数据（是真 Live 视频）
    - still 的 EXIF DateTimeOriginal 与 MOV 的 creation_time 差 ≤ 3 秒
    - still 尚未被别的视频占用（一对一）
  目的：文件名被批量改名 / 剧照被转成 .jpg 后名字对不上的场景。

优先级：第 1 级命中就锁定，绝不被第 3 级改写。
```

> **为什么不把 content-identifier 当主策略**：实测本机 40 张 HEIC 命中 0（多半是导出/改名工具把 maker note 洗掉了）。把主策略建立在一个"可能不存在"的字段上，会导致用户的库大面积配不上对。反过来，文件名 stem 在所有导出路径下都稳。

### 3.2 关键实体

```sql
-- 资产（一行 = 网格里的一张"照片"）
assets(
  id INTEGER PK,
  dir TEXT, name TEXT, stem TEXT,          -- 用于重扫时快速定位
  kind TEXT,        -- still | live | video | raw | other
  still_path TEXT, still_ext TEXT, still_size INTEGER, still_mtime INTEGER,
  video_path TEXT, video_ext TEXT, video_size INTEGER, video_mtime INTEGER,
  pair_confidence TEXT,                    -- exact | metadata | heuristic | orphan
  width INTEGER, height INTEGER,
  captured_at INTEGER,                     -- EXIF DateTimeOriginal 优先，其次文件时间
  captured_at_src TEXT,                    -- exif | filename | mtime
  gps_lat REAL, gps_lon REAL,
  camera_make TEXT, camera_model TEXT, lens TEXT,
  iso INTEGER, fnumber REAL, exposure REAL, focal_len REAL,
  orientation INTEGER,
  duration_ms INTEGER,                     -- live 视频时长
  still_image_time_ms INTEGER,             -- MOV 里的关键帧时刻
  vitality_score REAL,
  content_id TEXT,                         -- 有就存
  phash INTEGER,                           -- 感知哈希（去重/相似）
  is_favorite INTEGER DEFAULT 0,
  is_hidden INTEGER DEFAULT 0,
  place_state TEXT,                        -- local | cloud_placeholder | cloud_error | missing
  live_state TEXT,                         -- ok | video_missing | provider_down
  indexed_at INTEGER, content_rev INTEGER  -- 增量重扫用
)

-- 缩略图/预览缓存登记（真正的字节在磁盘缓存目录）
cache_entries(
  asset_id INTEGER, tier TEXT,             -- grid256 | grid512 | screen | poster
  key TEXT,                                -- 缓存键 = hash(path|mtime|size|tier|encoder_ver)
  bytes INTEGER, format TEXT, w INTEGER, h INTEGER,
  created_at INTEGER, last_hit INTEGER, hit_count INTEGER
)

-- 未来：AI 分类（v1 建表但不写入，避免以后迁移）
ml_labels(asset_id, label TEXT, score REAL, model TEXT, model_ver TEXT, created_at)
ml_embeddings(asset_id, model TEXT, dim INTEGER, vec BLOB, quant TEXT, created_at)  -- f32/int8
ml_jobs(asset_id, task TEXT, state TEXT, tries INTEGER, updated_at)
ml_models(id TEXT PK, name TEXT, sha256 TEXT, path TEXT, downloaded_at INTEGER)

-- 扫描状态（支持"上次扫到哪"）
scan_roots(id, path, last_scan_at, file_count, state)
scan_files(root_id, dir, name, size, mtime)   -- 轻量快照，用于增量 diff
```

索引：`assets(captured_at)`、`assets(kind)`、`assets(phash)`、`assets(dir, stem)`、`cache_entries(key)`。
SQLite 开 WAL；索引过程在单写线程里批量事务（1000 行/事务），避免频繁 fsync。

### 3.3 增量扫描

- 用 `ReadDirectoryChangesW`（Rust `notify` crate）监听已注册的根目录，变更打标；
- 目录扫描只读元数据（`FindFirstFileEx` + `FILE_ID_BOTH_DIR_INFO` 批量取枚举），**绝不 open 文件内容**；
- diff 策略：`(相对路径, size, mtime)` 三元组；新增入队、消失标 `missing`、mtime 变了则失效该资产的 cache 行；
- 全库重扫 17k 文件的目标：≤ 2 秒（只有元数据）。

## 4. 缓存与渲染架构（性能核心）

### 4.1 三级图像 + 一条视频预览

| 层级 | 尺寸 | 用途 | 生成时机 | 目标耗时 |
|---|---|---|---|---|
| **poster** | 512 长边 | 网格占位、转场起点 | 滚动可见时最高优先 | 从 MOV 抽帧 ≤ 15ms；从 HEIC ≤ 450ms |
| **grid** | 256 / 512 两档（DPI 自适应） | 网格单元 | 可见 + 前后各一屏预取 | 同上（可与 poster 合并） |
| **screen** | 2048 长边 | 全屏立即显示 | 打开大图时 | ≤ 400ms（多数命中缓存） |
| **full** | 原始分辨率 | 放大到 100%+ | 用户真的放大时才解 | 按需，解码完成前先放大 screen 层（渐进清晰） |
| **liveclip** | 720p / H.264 | 悬停/播放预览（WebView 里原生 `<video>` 播） | 后台低优先批量 | 每段 ≤ 150ms（硬编） |

**格式选择（实测驱动）**：用 **JPEG**（WIC 或 `image` crate 硬/SIMD 编码），不用 WebP —— 实测 Pillow 编 512px WebP 要 121ms，而 JPEG 只要个位数毫秒。缓存体积可由质量参数权衡。AVIF 只在"长期归档缓存"场景考虑（编码太慢）。

**磁盘缓存布局**：

```
%LOCALAPPDATA%\LivePhoto\cache\
  v1\
    grid\aa\bb\<hash>.jpg
    screen\aa\bb\<hash>.jpg
    clip\aa\bb\<hash>.mp4
  index.db            （SQLite）
  index.db-wal
```

- 缓存键 = `blake3(绝对路径 + mtime + size + 层级 + 编码器版本)` → 文件内容变了 key 自然失效，不需要手动清理；
- 容量上限默认 3GB（可配），LRU 淘汰用 `cache_entries.last_hit`；
- 命中的缓存行写回 `hit_count`，用于"热点优先预取"。

### 4.2 线程/任务模型

```
┌─ UI 线程（WebView2 / 或 wgpu 渲染线程）        绝不阻塞，不做 IO、不做解码
│
├─ 索引线程 ×1         目录枚举、增量 diff、写 SQLite（单写者）
│
├─ 解码工作池 ×N         N = clamp(物理核数-2, 2, 8)，本机 = 6
│   ├ 优先级队列：可见格 > 前后一屏预取 > 全屏请求 > 后台补全
│   ├ 任务可取消：用户快速滚过时，取消尚未开始的任务
│   └ 每个任务：读原文件 → 解码 → 缩放（SIMD fast_image_resize）→ 编码 → 落盘 → 通知 UI
│
├─ 视频工作池 ×2        MF 硬解抽海报帧 / 生成 H.264 预览片段
│
├─ 元数据线程 ×1        EXIF/GPS/MOV box 解析（只读文件头，通常 < 64KB）
│
└─ （未来）推理线程 ×1~2  ONNX Runtime，批量吃已缓存的 224px 缩略图
```

**关键约束**：
- 同一时刻只有一个线程碰同一个原文件（按 path 加锁），避免磁头/缓存抖动；
- 解码池的总内存配额（例如 512MB）用信号量控制，避免 8 张 12MP 同时展开爆内存；
- 所有跨线程结果只通过"缓存键 + 队列"传递，不传大 buffer。

### 4.3 网格渲染

- **虚拟化**：只挂载视口 + 前后各一屏的单元格，DOM 节点数恒定（~200 个），滚动时复用；
- **图集（atlas）**：可选进阶优化 —— 把多张 256px 缩略图打包进 2048² 纹理，一次上传，网格用 UV 取子矩形。WebView 里用 `img` 更简单，先不做 atlas，只在实测掉帧时才上；
- **滚动**：容器 `transform: translate3d(0, -offset, 0)`，只动合成层，不触发布局；格子用固定宽高 + `object-fit: cover`；
- **`will-change` / `contain: strict`** 限制重绘范围；
- **120Hz**：确保不出现"每帧 JS 工作 > 8ms"，滚动用 `passive` 事件 + `requestAnimationFrame` 合并；
- 网格单元比例：Apple 相册是**正方形裁切**，点开才看原比例 —— 照抄这个，视觉密度和"整齐感"就出来了。

### 4.4 Live Photo 播放引擎（本方案体验的关键）

**剧照对齐**：从 MOV 元数据拿到 `still_image_time_ms`（本机样本解析到了这个字段）。播放时：
- 起播点 = `still_image_time - 预卷(约 600ms)`，让画面从"剧照前后"开始动，观感上照片"活"了；
- 播放到片段末尾 → 回到剧照帧（不是黑屏，不是首帧）；
- 松手立即停止并淡回剧照（`opacity` 过渡 120ms）。

**三种播放路径（按可用性降级）**：

| 路径 | 条件 | 实现 | 观感 |
|---|---|---|---|
| A · 原生播放 | 系统有 HEVC 扩展（本机有） | MF 解码 → 原分辨率，声音直出 | 最佳，原始质量 |
| B · 预览片段 | 无 HEVC 解码能力 | 后台把 MOV 转成 720p H.264 缓存，WebView 原生播 | 略降质，但**播放必然流畅** |
| C · 外部播放器 | 用户想全质量或片段异常 | 调起系统播放器打开 MOV | 兜底，不卡死 |

> 路径 B 有个额外好处：H.264 在 WebView2/Chromium 里是**硬解原生支持**的，播放 100% 平滑，不需要我们在渲染层做任何视频合成。这比"自己把 YUV 帧推给 GPU"省掉一整块复杂度，是本方案刻意的取舍。
>
> 代价：需要为每个 Live Photo 生成一份 ~200KB 的预览片段。10,000 张 ≈ 2GB（可设上限、可后台闲时生成、可只给"hover 过的"生成）。

**音频**：默认 hover 预览静音；点击/按住播放时出声；工具栏有全局静音开关；记住用户选择。
**电池/性能**：hover 预览只在"静止 400ms 后"触发，滚动中绝不播放；同一时刻只允许 1 个格子在播。

### 4.5 云端占位（iCloud / OneDrive）处理

这是本机实测踩到的真实场景，**必须在一开始就设计进去**，否则用户第一次打开自己的 iCloud 相册就是一片报错。

**探测**（不打开文件，只读属性）：

```rust
attrs & FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS  // 0x400000
attrs & FILE_ATTRIBUTE_OFFLINE                // 0x1000
attrs & FILE_ATTRIBUTE_RECALL_ON_OPEN         // 0x40000
```

**状态机**：

```
local           → 正常流程
cloud_placeholder → 网格显示"云朵"角标 + 低清/空白占位；不主动下载
   用户点击/滚到 → 可选策略：
     (a) 显式"下载"按钮（推荐，尊重流量）→ CfHydratePlaceholder / 直接 open 触发同步引擎拉取
     (b) 自动拉取（可配置，默认关）→ 小并发（≤2），带进度
   拉取中：角标转进度；拉取完成 → 转 local 并生成缩略图
   拉取失败 0x8007018B（cloud file provider is not running）
     → 明确告知："iCloud 客户端未运行，请先启动 iCloud for Windows"
       （这正是本机当前的状态，必须给出人话提示，而不是抛 Errno 22）
```

**要点**：
- 索引阶段**永远不 hydrate**：只列目录 + 读属性，所以即使是 100% 云端的库也能秒开网格；
- 网络/云端目录的元数据读也可能很慢 → 目录枚举放独立线程 + 超时 + 可取消；
- 绝不在 UI 线程上碰任何可能是占位的文件。

### 4.6 Windows 平台细节

- **文件枚举**：`FindFirstFileExW` + `FindExInfoBasic`（不取 8.3 短名，快很多）+ `FIND_FIRST_EX_LARGE_FETCH`；
- **长路径**：全程用 `\\?\` 前缀 / `std::os::windows::fs` 扩展，避免 260 字符限制（相机导出的目录名很长）；
- **属性读取**：`GetFileAttributesExW` 一次拿属性+大小+时间；
- **HI-DPI**：Per-Monitor V2 DPI awareness；
- **暗色**：跟随系统 `AppsUseLightTheme`；
- **单实例** + 拖拽目录进窗口 + 右键"用 LivePhoto 浏览器打开"（可选注册）；
- **只读原则**：除缓存目录外不写任何位置；删除/移动一律走"回收站"且二次确认（v2 再说）。

| 维度 | **Tauri v2 + Rust 核心**（推荐） | 纯 Rust + wgpu/egui 自绘 | WinUI 3 (.NET) | Electron |
|---|---|---|---|---|
| 安装包 | **~10MB** | **~12-20MB**（含 CJK 字体 +10MB） | ~2MB（依赖 runtime）或 ~80MB 自包含 | 150MB+ |
| 冷启动 | ~300-600ms | **~150-300ms** | ~400-800ms | 1-2s |
| 内存占用 | 150-250MB | **60-120MB** | 120-200MB | 300-500MB |
| 滚动流畅度 | 很好（Chromium 合成器） | **最好（完全自控帧节奏）** | 好（GridView 虚拟化） | 很好 |
| UI 达到"苹果感"的成本 | **低**（CSS：backdrop-filter / 圆角 / 弹性动画 / 系统字体免费） | 高（模糊、圆角、文本排版、动画全要自绘） | 中（Fluent 风格，是"微软感"不是"苹果感"） | 低 |
| HEIC | Rust 侧 WIC/libheif 解码后供给 | 同左 | WIC 直读 | 同 Tauri |
| HEVC 播放 | 转 H.264 预览片段，原生 `<video>` | MF 解码 → GPU 纹理 | MF/EVR | 同 Tauri |
| 前置依赖 | rustup + MSVC Build Tools + Node/pnpm | rustup + MSVC Build Tools | **需装 .NET SDK（本机没有）** | Node |
| AI 推理（未来） | Rust `ort`（ONNX Runtime）+ DirectML | 同左 | ONNX Runtime .NET | 同左 |
| 主要风险 | WebView2 内存/视频能力边界 | 开发工期长，UI 打磨慢 | 本机无 SDK；生态偏微软风 | 太重，违背"轻量级" |

**推荐 Tauri v2**，三条理由：
1. 你的"轻量级"目标由**不打包 Chromium + 共享系统 WebView2 + 零编解码器打包**共同满足，安装包能压到 10MB 级别；
2. "苹果相册体验"里最贵的是**视觉质感**（半透明材质、圆角、阴影、缓动曲线、中文排版），这些在 CSS 里是几十行，在自绘 GUI 里是几千行；
3. 重活（HEIC/HEVC 解码、缓存、SQLite、ONNX 推理）本来就在 Rust，栈的选择不影响这部分的性能上限。

**如果你更看重极致轻量（内存 <100MB、单 exe 无 WebView2）**，选纯 Rust + wgpu 方案，架构的 §3/§4 完全复用，只换 §4.3 的渲染层，UI 工期 +1.5~2 倍。

## 6. 性能预算与验收方法

每个里程碑都要有可复现的量化验收，不能靠"感觉挺流畅"。

| 指标 | 目标 | 怎么测 |
|---|---|---|
| 冷启动 → 首屏骨架可见 | ≤ 800ms（有缓存） | 埋点 `main()` → 首帧 `paint`，跑 20 次取 p50 |
| 冷启动 → 首屏有真实缩略图 | ≤ 1.5s | 同上 |
| 全库首次索引（17k 文件，仅元数据） | ≤ 2s | 计时，断言无文件内容读取（用 Process Monitor 复核） |
| 缩略图吞吐 | ≥ 8 张/秒·12MP HEIC（8 核） | 复用 `tools/livephoto-bench.py` 的方法，改到 Rust 侧 |
| 滚动帧率 | 60fps 稳定（120Hz 屏 120fps） | 录帧时间戳，统计 p99 帧时间 ≤ 16.7ms；0 次 >50ms 卡顿 |
| 大图打开 → 清晰 | ≤ 200ms（缓存命中）/ ≤ 500ms（需解码） | 埋点 |
| Live 起播延迟 | ≤ 100ms | 按下 → 首帧上屏 |
| hover 预览触发 | 静止 400ms 后开始，滚动中 0 次误触发 | 事件日志 |
| 常驻内存（5 万张库） | ≤ 400MB | 任务管理器 / `Get-Process` |
| 安装包体积 | ≤ 15MB | 构建产物 |

**对照基线**：Windows 自带"照片"App 打开同一个 `F:\DCIM` 的表现，作为"不能比它差"的底线；Apple 相册的行为作为上限参考。

## 7. 未来：模型给照片分类（架构预留 + 落地方案）

这块**不塞进 v1**，但 v1 的数据模型和线程模型要为它留好插槽（§3.2 已建表，§4.2 已留推理池）。

### 7.1 为什么这个应用做 AI 分类特别便宜

因为缩略图管线已经是现成的：**分类模型需要的 224×224 输入，正好是缓存里已有的小图**。不需要额外的原图解码（那才是最贵的一步，实测 417ms/张）。这直接把"给 5 万张照片分类"从"几小时"压到"按缓存读写速度算"。

### 7.2 能力路线（按投入产出排序）

| 阶段 | 能力 | 方案 | 依赖 |
|---|---|---|---|
| **A1** | 智能相簿（人物/食物/宠物/文档/风景/截图…） | **零样本分类**：CLIP/SigLIP 图像编码器 + 预置的文本标签向量，余弦相似度出标签。改标签不用重训模型 | 一个 ViT-B/32 ONNX（~350MB fp16 ~170MB） |
| **A2** | 自然语言搜图 | 同上模型，文本编码器把查询词编码，和图像向量比相似度；SQLite 存向量，暴力扫 f32 向量 5 万条 ≈ 毫秒级 | 同上（含文本塔） |
| **A3** | 相似照片 / 去重 | 复用 A2 的向量 + §3.2 的 pHash 做粗筛 | 无新增 |
| **A4** | 人脸 / 人物相簿 | SCRFD 检测 + ArcFace 512d 嵌入 + 层次聚类；人脸裁切图另存缓存 | 两个小 ONNX（各 ~10-30MB） |
| **A5** | 效果打分（挑最好的那张） | 小回归/分类模型（清晰度、曝光、构图），用于连拍优选 | 小模型 |
| **A6** | 本地语义标签微调 | 用户纠正过标签后做 kNN / 逻辑回归头部，不重训主干 | 无 |

**推荐起点：A1 + A2 合并做**，一个 SigLIP/CLIP ONNX 就同时拿到分类和搜索，性价比最高。

### 7.3 运行时与硬件加速

- **ONNX Runtime**，Rust 侧用 `ort` crate；
- **DirectML Execution Provider** 做 GPU 加速（Windows 上跨厂商：NVIDIA/AMD/Intel 通吃），CPU EP 兜底；
- 批大小 16~32，fp16 优先（DirectML 支持好、显存省一半）；
- 实测预期：ViT-B/32 在 DirectML 上一批 16 张 ≈ 数十毫秒级 → 5 万张 ≈ 几分钟；CPU 上 ≈ 十几分钟，都可接受（后台闲时跑）；
- 无 GPU 或用户拒绝时：降级到"仅对新照片做增量"。

### 7.4 存储与索引

- 向量：`f32[512]` = 2KB/张 → 5 万张 = 100MB；**int8 量化** → 25MB，精度损失对分类/搜索几乎无感，默认开量化；
- 检索：先用 pHash / 颜色直方图粗筛候选（几十张），再算精排 —— 避免全表扫；
- 标签：`ml_labels` 一行一标签一分数，UI 侧按分数倒序 + 阈值过滤；
- **可重算性**：所有 AI 产物都是"派生数据"，模型升级 → `model_ver` 变了 → 后台重算，原文不受影响。

### 7.5 UI 集成（复用现有交互）

- 左侧边栏新增"智能相簿"分组（无模型时整组不显示，绝不出现空壳）；
- 搜索框输入自然语言 → 结果以正常网格呈现（复用网格组件，零新增渲染路径）；
- 每张图的信息面板显示 top-3 标签 + 置信度；
- 右键"这不是XX" → 写负样本，供 A6 微调；
- **首次启用**：弹一次说明（模型大小、是否下载、全程本地、可随时关闭），下载走后台 + 断点续传 + sha256 校验；未下载时该功能入口置灰并说明原因。

### 7.6 隐私

全部本地推理，默认**零网络请求**；唯一的网络行为是"用户显式点击下载模型"。这一点写进 README 和首启说明。

| 12MP HEIC 解码慢（实测 417ms/张） | 首屏体验差 | 两级缓存 + 后台渐进 + 可见优先；Live Photo 封面优先从 MOV 抽帧（快 10-100 倍）；只在真正需要时才解全图 |
| HEVC 解码依赖系统扩展 | 没装扩展的机器无法播放 | 探测能力 → 自动走路径 B（H.264 预览片段）；再不行走路径 C；文档给出免费扩展的安装指引 |
| WebView2 未安装（极少见） | 应用起不来 | 启动时检测，给出引导（Win11 默认已内置；Tauri 也支持内置 bootstrapper） |
| 云端占位文件（本机已复现） | 一片报错/卡死 | §4.5 的状态机；索引阶段绝不读内容；明确的"iCloud 未运行"提示 |
| 用户文件被批量改名 | 配对率下降 | 三级配对策略 + 置信度标注；UI 上对低置信配对不显示 LIVE 角标 |
| 内存爆（大库 + 大图 + 解码池） | 卡顿/崩溃 | 显式内存配额 + 信号量；纹理 LRU；全图只在放大时解 |
| Tauri/Rust 生态踩坑 | 工期延误 | M0 先把四个高风险点验证掉再往下做，不验证不开工 |
| 法律/授权 | 发布受阻 | 不打包 FFmpeg（默认走系统编解码器）；若必须打包，用 LGPL 动态链接 + 声明，且 HEVC 专利问题单独评估 |

## 10. 需要你确认的问题

1. **技术栈**：接受推荐的 **Tauri v2**？还是更看重内存/体积，走 **纯 Rust + wgpu 自绘**？
2. **目标数据源**：这个工具主要给你浏览哪一类目录？
   - (a) `F:\DCIM` 这种**真实导出/整理过的库**（HEIC+MOV 配对完整）
   - (b) `C:\Users\lms\Pictures\iCloud Photos` 这种 **iCloud 云端占位库**（需要下载才能看）
   - (c) 两者都要
3. **是否接受"预览片段缓存"**：为流畅播放，需要给每个 Live Photo 生成一份 ~200KB 的 H.264 预览（10,000 张 ≈ 2GB 缓存）。可接受，还是希望严格零额外占用（那就只在打开时实时转码，起播会慢 ~200ms）？
4. **v1 范围**：`F:\DCIM` 里还有 6430 个 NEF(RAW) 和 6409 个 JPG —— v1 要不要一并纳入浏览（RAW 只显示内嵌预览）？还是严格只做 iPhone 的 HEIC/JPG + MOV/MP4？
5. **要不要我现在就开工**：确认栈之后，我建议直接做 **M0 spike**（2-3 天量级），用一个真实可跑的最小程序把四个关键数字量出来，再决定后续细节。
