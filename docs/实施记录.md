## 1. 性能故事：为什么它比 Windows 原生文件夹还快

这是本项目最值得说的一件事，而且它不是"优化出来的"，是**设计第一性推出来的**。

### 1.1 结论先行

| 环节 | 实测 | 为什么能这么快 |
|---|---|---|
| 扫描 17,159 个文件 | **257 ms**（66,769 文件/秒） | **只读目录元数据，从不打开文件内容** |
| 已有缓存的缩略图 | **14,896 张/秒** | 就是读硬盘上的小 JPEG，不解码 |
| 网格滚动（5000 格，真实照片） | **58.5 fps**，p50 = 16.7ms | 虚拟化 + GPU 合成，跑满 60Hz vsync |
| 7832 个资产同时存在时的 DOM 节点 | **54 个** | 行列表虚拟化，只挂可见区 |

### 1.2 关键洞察：Windows 资源管理器慢在哪

资源管理器要显示缩略图，必须**打开每个文件**去问 shell 缩略图提供程序
（HEIC 会走 HEIF 扩展、视频要走 Media Foundation），这是一条很重的链路：

- 每个文件都要建立解码器、解码内容、生成缩略图、写图标缓存；
- 目录里一旦有**云端占位文件**（iCloud/OneDrive），打开就可能是"触发下载"甚至
  `0x8007018B The cloud file provider is not running`，界面只能干等；
- 它必须对所有文件类型一视同仁，不能"只处理你正在看的那一屏"。

而我们的做法是从一开始就把这些成本切掉了：

**① 索引阶段只碰元数据。** 用 `FindFirstFileExW` + `FindExInfoBasic`（不取 8.3 短名）
+ `FIND_FIRST_EX_LARGE_FETCH`（内核一次多取几批目录项）批量读目录项。
这条路的好处不只是快，更是**永远安全**：
本机 iCloud 相册目录里 663 个文件是云端占位（属性 `0x401620`），
列目录没问题、读内容必炸 —— 而我们的索引阶段根本不读内容，所以整库在云上也能秒开网格。

这条纪律在代码里是硬性的：`core/src/files.rs` 顶部就写着"绝不打开文件内容"。

**② 只解你在看的那一屏。** 前端滚动时把"可见格子的 id 集合"报给后端，
后端自动外扩两屏做预取，**不在需要集合里的待办会被直接丢弃**（滚过即弃）。
实测证据：真实 App 清空缓存后打开 `F:\DCIM`，30 秒内生成 111 张缩略图
（窗口可见区正好 8×14 = 112 格），**然后就不动了** —— 全程没碰其余 7832 个资产。

**③ 三级图源，让"等待"从界面里消失。**

```
网格格子 ──先用磁盘缓存的 512px 顶上（1ms）──> 滚到哪解到哪
全屏查看 ──先用已缓存的 512px 顶上（零等待）──> 同时后台算 2048px ──> 算好无缝替换
```

这条设计是被实测逼出来的：HEIC 解码 **889ms/张**（JPG 只要 135ms，差 6.6 倍），
而且**加线程几乎没用**（6 线程只有 1.4× 加速，跨进程也只有 2×）。
既然单张解码快不了，那就**绝不让用户等它** —— 用已经算好的低清图顶上。

**④ 热缓存让"滚到就有"真正成立。**
冷缓存下 300 张缩略图要 29 秒（10.3 张/秒），而热缓存下 300 张只要 **0.02 秒**。
所以设计目标不是"把解码做快"，而是"**尽快让看过的区域变热**"。
1 万张的缓存约 300MB，存在 `%LOCALAPPDATA%\LivePhoto\cache`，
是纯派生数据 —— 整个删掉只损失时间，不丢任何照片。

**⑤ 渲染层不给自己找麻烦。**
从"等宽网格"改成**行列表**（日期标题行 + 照片行），每行带 `y/h`，二分查找定位可见区。
好处是滚动时每帧只在两端增删格子（7832 资产只挂 54 个节点），
而日期分组、时间轴、Ctrl 缩放全都天然兼容这个模型。

### 1.3 一句诚实的话

资源管理器做的事情比我们多：它要覆盖所有文件类型、网络路径、图标与 shell 集成。
我们的快，来自**明确放弃那些事**，只把"看 Live Photo"这一件事做到极致。
这个对比是"为特定任务特化 vs 通用"，不是"我们比微软写得好"。

## 2. 决策记录（按时间顺序）

### D1 · 技术栈选 Tauri v2

- **背景**：Windows 端、要求轻量 + 流畅 + 苹果相册质感，未来要加 AI 分类。
- **选项**：Tauri v2 / 纯 Rust + wgpu 自绘 / WinUI 3 / Electron。
- **决定**：Tauri v2（Rust 核心 + WebView2 渲染 UI）。
- **依据**：Win11 自带 WebView2，安装包能压到 10MB 级；"苹果质感"最贵的是视觉
  （半透明材质、圆角、缓动、中文排版），CSS 里几十行、自绘 GUI 里几千行；
  重活（解码/缓存/索引/推理）本来就在 Rust，栈的选择不影响性能上限。
- **后果**：内存比纯原生高（约 150-250MB）；**HEVC 画面怎么送进 WebView 成为待解风险**。

### D2 · 不做"导入"，文件夹就是库

- **背景**：用户明确质疑"为什么要导入，不能直接浏览文件夹吗"。
- **决定**：无库、无导入、无复制。扫描只读元数据；缓存是纯派生数据、可随时删。
- **依据**：扫描 17k 文件只要 257ms，所以"打开文件夹"这个动作本身几乎没有代价，
  没必要引入"库"这一层。
- **后果**：全部扫描/配对逻辑必须能在几百毫秒内完成 → 逼出了 D3。

### D3 · 索引阶段绝不打开文件内容

- **背景**：需要判断文件是不是"云端占位"、需要拿宽高。
- **决定**：只用 `dwFileAttributes` 判断占位；宽高一律不从文件里读。
- **依据**：本机 iCloud 目录 663/666 个文件是占位，读内容直接 `Errno 22`（0x8007018B）。
  而且 M0 实测"只创建 HEIC 解码器"也要 9ms/张 + 首次 155ms 冷启动。
- **后果**：整库在云上也能秒开网格；代价是宽高、EXIF 需要后续按需补齐（尚未做）。

### D4 · HEIC 解码必须在 STA 套间

- **背景**：Rust 里调 WIC 解 HEIC 时**永久阻塞**（30s+ 不返回、进程 0 CPU）。
- **排查过程**：先用 2×2 对照排除"中文路径"（结论：中文路径没问题），
  再用 PowerShell 5.1（STA）跑 WPF `BitmapDecoder` 成功解出 4032×3024，
  确认是**套间模型**问题，不是文件、不是路径、不是我们的代码。
- **决定**：每个解码工作线程自己 `CoInitializeEx(STA)`，各自持有自己的 WIC 工厂
  （`wic::with_factory` 用 thread_local；`WicFactory` 刻意不实现 `Send`/`Sync`）。
- **依据**：HEIF 解码器会回调调用方套间，只有 STA 的阻塞等待会顺带泵消息。
- **后果**：线程模型被这条约束锁死；也顺带解释了"为什么并行加不上去"。

### D5 · 绝不在 Tauri 主线程初始化 COM

- **背景**：把 `com_init()` 放进 `run()` 后，App 启动即崩：
  `OleInitialize failed! Result was: RPC_E_CHANGED_MODE`。
- **依据**：tao 创建窗口时会调 `OleInitialize`（要求 STA），主线程已被改成 MTA 就崩。
- **决定**：主线程只做 UI；解码初始化一律在 `media::worker_init()`（工作线程里）。

### D6 · 缩略图工作池用"少量常驻线程"，不是"越多越好"

- **背景**：直觉是线程越多越快。
- **实测**：HEIC 6 线程只 1.4×；MF 抽帧 6 线程比单线程**还慢**（0.39×）；
  6 个独立进程也只有 2.0×。
- **决定**：默认 **2 个常驻工作线程**（`LIVEPHOTO_WORKERS` 可调），
  视频任务走全局串行闸门。
- **后果**：单线程批量 10.3 张/秒（JPG 主导样本）；换来的是稳定 ——
  最慢帧/平均从 16× 收敛到 1.76×。

### D7 · 视频海报快路径默认**关闭**

- **背景**：`bench_mf_reuse` 独立测出 NV12 首帧只要 65ms（RGB32 222ms），
  而解 12MP HEIC 要 435~889ms —— 看起来"Live Photo 从 MOV 取海报"稳赚 6 倍。
- **实测打脸**：放进工作池与剧照解码并行后，视频路径变成 **≈3000ms/张**（慢 14 倍），
  整个池最慢帧飙到 6~8 秒、`最慢/平均` 从 1.76 恶化到 10.9。
  算术核对：`371×3000 + 1118×193 = 平均 885ms`，与实测 745~797ms 吻合 —— 抖动全来自这条路。
- **决定**：默认关闭（`LIVEPHOTO_POSTER_FROM_VIDEO=1` 才开）。
- **教训**：**独立测得好看的优化，必须在真实管线里复测才能上。**

### D8 · 滚轮由前端自己接管

- **背景**：用户反馈"没法上下滚动"。埋点显示 `wheel` 计数在涨、`deltaY=133`，
  但 `scroll` 计数恒为 0、`scrollTop` 恒为 0。
- **排查**：自检确认滚动器本身完全正常（`overflow-y: scroll`、
  `scrollHeight 275,569 > clientHeight 844`、赋值 `scrollTop=3000` 生效）。
  即"事件到了、却不触发原生滚动"，在 WebView2 里无法再往下查（DevTools 未开）。
- **决定**：`preventDefault()` + `scrollTop += deltaY` 自己滚。
- **后果**：行为可预期；代价是**失去系统原生惯性滚动**（换来了以后自己做惯性的口子）。

### D9 · 网格改成"行列表"模型

- **背景**：要加日期分组（时间轴），而等宽网格模型塞不进"标题行"。
- **决定**：布局变成 `行 = 日期标题行 | 照片行`，每行带 `y/h`，二分查找定位可见区。
- **后果**：日期分组、时间轴、Ctrl 缩放全部天然兼容；代价是任何改变 `cols`/`cellSize`
  的操作都必须**重建全部已挂载格子**（见踩坑 K3）。

### D10 · 不用 `contain: strict`

- **背景**：为了滚动性能给 `#grid` 加了 `contain: strict`。
- **问题**：`strict` 含 `contain: size`，对滚动容器不安全（也是滚轮失灵的嫌疑之一）。
- **决定**：降级为 `contain: layout paint`；实测 58.5fps 本来也不是靠它挣来的。

### D11 · Live Photo 播放：直接用 `<video>` 播原始 HEVC，不转码

- **背景**：M4 的最大未知是"HEVC 画面怎么送进 WebView"。方案里列了两条有代价的路：
  转 720p H.264 预览缓存（稳，但 1 万张约 2GB），或原生叠加窗口跑 MF（无缓存，但圆角/叠加 UI 很麻烦）。
  我打算先实测再定，不拍脑袋。
- **测试方法**：加一个支持 **HTTP Range** 的自定义协议 `media://`（`<video>` 要 seek 就必须有分段请求），
  用 `<video>` 指向真实的 Live Photo MOV，读回 metadata / play() / currentTime。
- **实测结果（`ui-media-selftest.json`）**：

  | 检查 | 结果 |
  |---|---|
  | `canPlayType('video/mp4; codecs="hvc1"')` | **""（报不支持）** |
  | 实际 `loadedmetadata` | ✅ 成功 |
  | 实际 `play()` | ✅ resolved，`readyState=4` |
  | 分辨率 / 时长 | 1440×1920 / **1.965s**（与 MOV 元数据解析的 1940ms 吻合） |
  | 实际播放进度 | `currentTime` 前进到 0.66s |

- **决定**：**直接用 `<video>` 播放原始 MOV**，不做任何转码。
- **依据**：**`canPlayType` 对 HEVC 的返回值是误导** —— 它说"不支持"，真实播放却完全正常。
  如果只信 `canPlayType` 就会白白去做 2GB 的转码缓存。
- **后果**：省掉整条转码链路与约 2GB 缓存；**声音是原生的**；播放走系统 HEVC 扩展的硬解。
  唯一前提是自定义协议必须支持 Range（已实现并验证）。
- **教训**：**能力查询 API 不能当作能力证据，必须实际跑一遍。**

### D12 · 网格悬停预览用"共享 `<video>` + 380ms 延时"

- **依据**：Apple 相册的悬停预览手感来自两点 —— 滚动中绝不触发、静止一下才播。
- **决定**：只有一个 `<video>` 元素，悬停 380ms 后定位到该格并静音循环播放；
  滚动或移开立即停止并清 `src`。
- **理由**：每格一个 `<video>` 会瞬间建几十个解码器（M0 已证系统解码器不能并行）。

### D13 · 全屏层延迟优化：真凶是"排队竞争"，不是解码慢

- **现象**（用户反馈）：全屏左右切换时"先显示小图、过一会才出大图"，延迟明显。
- **第一步：量清楚**。加了 `screenLatency` 埋点（从请求到可显示），并且**必须用从没被请求过的位置** ——
  第一次跑用第 0 张，结果测出 22ms，其实是前面自检已经把它缓存了，量到的是命中而非冷启动。
  换成第 500 张后才拿到真数字。
- **优化前后（`ui-screen-selftest.json`）**：

  | 指标 | 优化前 | 优化后 |
  |---|---|---|
  | 冷启动显示大图 | **2332 ms** | **280 ms** |
  | 切换到相邻张 | **615 ms** | **30 ms** |
  | 切换端到端 | 685 ms | 73 ms |

- **第二步：拆解成本**（`bench_screen`，HEIC p50）：

  | 阶段 | 耗时 | 占比 |
  |---|---|---|
  | 解码 @2048 | **896 ms** | **85%** |
  | JPEG 编码 @2048 | 264 ms | 25% |
  | 端到端 @2048 | 1050 ms | — |
  | 端到端 @1536（候选替代） | 989 ms | 只快 6% |
  | decode@512 vs decode@2048 | 809 vs 897 ms | **几乎相同** |

  → **解码成本与目标尺寸无关**（WIC 必须先解整张 12MP 图），
  所以"降低全屏尺寸"几乎没用、"换更快的编码器"最多省 25%。
- **第三步：定位真正的浪费**。2332ms 里远超单张 1050ms 的部分是**排队等待** ——
  自检时工作池同时在算网格缩略图（一屏）+ 我请求的 5 张全屏层，只有 2 个工作线程，
  而我最初把全屏中心任务的优先级设成和网格可见一样（都是 0），于是被网格抢了。
- **决定**：优先级重排 —— 全屏 `center=0 / ±1=1 / ±2=2`，网格可见降到 `4`、网格预取 `8`。
  依据：**用户在看全屏时网格是隐藏的、不会滚动**，网格任务没有任何理由和用户正在等的那张抢线程。
- **仍未解决**：跨越 3 张以上的跳转不在预加载半径内，会退化成冷启动（HEIC 约 1s）。
  这是预加载的固有限制；目标场景是"左右逐张浏览"，那个场景已经做到 30ms。

### D14 · 底部胶片条：把"等多久"变成可预期

- **背景**（用户提出）：全屏层单张 HEIC 约 1050ms、产出速度约 4.7 张/秒，切快了必然要等。
  用户的诉求是"给个心理预期"，而不是继续压延迟。
- **决定**：查看器底部放一条胶片条，显示当前张前后各 4 张，每张标注预加载状态：
  `cached`（已就绪，切过去是瞬间的）/ `busy`（正在准备，流光动画）/ `queued`（排队中）/ `idle`（未开始）。
  胶片条可点击跳转，当前张蓝色粗框。
- **关键实现约束**：胶片条用**网格层**（已缓存，永远瞬间出图），不额外消耗解码 ——
  否则就会出现"为了显示状态而拖慢看图"的蠢事。
- **后端支撑**：`ThumbPool` 增加 `in_flight_keys` 与 `states_of()`，命令 `screen_states`。
- **踩坑**：第一次实现里，后端返回的状态是 `cached`，而 CSS 选择器写的是 `.ready` ——
  **两边名字对不上**，于是 `.ready img { opacity: 1 }` 从未生效，
  所有非当前的已加载图都停在基础透明度 0.55（发灰）。用户直接看出"加载好的图不该偏灰"。
  修法：类名统一成后端返回的真实状态，并重新定义语义 ——
  **`busy` 也是已加载好的图，不该压暗**，只用流光表达进行中；只有 `queued`/`idle` 才压暗。

### D15 · 缓存加 LRU 上限（默认 4GB）

- **背景**：全屏层约 763KB/张，1 万张就是 **7.6GB**；网格层提到 1024 后是 147KB/张 ×1 万 = 1.5GB。
  缓存是纯派生数据，删掉只损失时间，但不该无限长。
- **决定**：`ThumbCache::enforce_limit(max_bytes)`，按"最旧优先"淘汰（mtime 近似 LRU）。
  启动时自动跑一次，另有 `evict_cache` 命令；同时清理残留 `.tmp`，
  并跳过最近 2 分钟内写入的文件，避免删掉正在读的。
- **验证**：用 1MB 上限做极限测试 → `127.7MB → 1.0MB，删除 1520 个文件`；
  恢复默认 4GB → `10.1MB → 10.1MB，删除 0 个`。
- **代价（诚实记录）**：那次极限测试把用户的缩略图缓存清空了。照片一张没动，
  但下次打开网格要重新填。**测试破坏性操作前应先隔离测试目录，而不是直接指向真实缓存。**

### D16 · 网格层 512 → 1024，兼作全屏占位（单层化）

- **背景**：用户反馈"切大图先看到一张糊的"。根因是网格层只有 512px，
  拉到全屏要放大 4.8 倍，明显发虚 —— 所以哪怕只等 400ms 也像"卡住"。
- **决定**：网格层提到 **1024**，同时承担两个用途：
  网格格子（最大 320px CSS × DPR 2.25 ≈ 720 设备像素，够用）
  + **全屏查看器的占位图**（只放大 2.4 倍，观感可接受）。
  全屏层 2048 仍然保留，算好后无缝替换 —— 也就是"先给一张能看的、再给一张最好的"。
- **实测代价**：缓存从 34KB/张 涨到 **147KB/张**；编码多约 60ms
  （瓶颈是解码，占 85%，所以总耗时只涨约 7%）。
- **注意**：层级名从 `grid512` 改成 `grid1024`，**旧缓存自动失效**（键里含层级名），
  由 D15 的淘汰逻辑清理。

### D17 · 预加载改成"严格从中心向两侧"（用户指出的 bug）

- **用户的观察**："不是应该从中间往两边预加载吗" —— 是对的，而我原来的实现是错的。
  我把优先级分成了**三档**（`center=0 / ±1=1 / 其余=2`），于是 ±2、±3、±4 同级，
  排序退化成"按 id 升序"，实际变成**先加载左边那几张**，而不是向两侧扩散。
- **决定**：优先级直接用**距离本身**（0,1,2,3,4），严格中心向两侧；距离相同再按 id。
- **同时把预加载半径从 4 收到 2**。依据：**解码是不可中断的** ——
  一张 HEIC 约 1s，worker 解到一半停不下来。半径越大、排队的远处任务越多，
  用户翻页时新中心越可能排在它们后面。半径 2 = 最多 5 张，2 线程下约 2 秒填满；
  半径 4 要 4 秒以上，期间翻页反而更容易等。
- **也回答了用户的另一个疑问**（"同时加载多张是不是更慢"）：是的，边际收益很小 ——
  实测 HEIC 解码 6 线程只有 1.4× 加速，第 2 个线程帮助有限；
  更关键的是"不可中断"决定了翻页延迟的下限（最坏要等当前那张解完，约 1s）。
- **测量说明（诚实记录）**：验证这轮改动时我**同时清空了 `grid1024` 与 `screen2048` 两个缓存**，
  于是整个观察窗口里应用都在重建网格缩略图，测到的全屏层 p50 = 3114ms
  **属于异常态、不是稳态**，不能当基线。教训：改优先级这类问题必须在**缓存已暖**的状态下测。

### D18 · 工作池的四处"记账"缺陷（同一个根因）

用户在调试过程中连续发现了四个现象，逐个排查后确认**根因是同一个**：
"提交任务"与"声明这个任务还需要"是**两个必须配对调用的接口**，而语言层面不强制，
于是每新增一条提交路径都漏掉了一步。

| # | 缺陷 | 现象 | 修法 |
|---|---|---|---|
| 1 | `request_grid` 只 `submit` 不 `pin` | 胶片条请求计数一直涨（297 次）却零产出 —— 工作线程的守卫"不在 wanted∪pinned 里就跳过"把任务静默丢弃 | 提交时同时 `pin`，关闭查看器时 `release_grid` |
| 2 | 胶片条优先级设成 50（低于网格可见 40） | "过了一会一排一起加载出来" —— 要等队列排空 | 提到 6（可见界面，高于远距离预加载） |
| 3 | 胶片条不复用已有图 | 为 56px 小图重复做约 900ms 解码（**解码成本与尺寸无关**） | 优先复用：全屏层已缓存→用它；否则网格层；否则占位 |
| 4 | 旧批次任务的优先级不降级 | **从最左侧慢慢往右加载**：旧中心仍是优先级 0，与当前中心并列，平局按 asset_id 升序 → 先做已翻过去的旧图 | 引入提交批次号，**最新批次权威地重新定义优先级** |

**第 4 点值得单独说**，因为它是"看起来像渲染问题、实际是队列问题"的典型：
去重逻辑写的是"只在新的优先级更小时才更新"（`if r.priority < q[pos].priority`），
而旧中心已经是 0、不可能更小，于是永远停在最高优先级。

**结论：这个池子的接口需要重构。** 应该把"提交"与"声明需要"合并成一个入口
（例如 `submit(jobs, keep_alive: bool)`，或由池子自己维护"当前焦点集合"），
让"提交但不声明"在类型上写不出来。否则第五个同类 bug 只是时间问题。

### D19 · 发布版白屏的真因：缺了 `custom-protocol` feature（不是前端问题）

- **现象**：`cargo build --release` 出来的二进制，窗口能起、WebView2 进程正常，
  但**前端完全没执行** —— 无任何诊断输出、缩略图缓存零增长、且**没有任何报错**。
  而 debug 版（走 Vite）一切正常。我一度怀疑是 Vite 给 module script 加的
  `crossorigin` 属性被 Tauri 自定义协议拦下（CORS），**这个猜测是错的**。
- **排查过程（值得记录，因为它靠的是"让程序自己作证"）**：
  1. 从 Rust 侧起一个后台线程，**不依赖任何 JS**，直接把
     "Rust 看到了几个窗口、窗口停在什么 URL 上"写进 JSON；
  2. 同一线程再 `eval` 一段脚本，把 `window.__LP_MAIN__` 标记、
     `document.scripts`、样式表数量回报上来。
- **一句话点破**：

  ```
  { label: 'main', url: 'http://tauri.localhost/' }    ← 修好后
  { label: 'main', url: 'http://localhost:1420/' }     ← 修好前（devUrl！）
  ```

  **release 二进制竟然在加载 devUrl。**
- **根因**：`tauri` crate 的 `build.rs` 里写着

  ```rust
  let dev = !custom_protocol;
  ```

  即"是不是 dev 模式"**不由 release profile 决定，而由 `custom-protocol` 这个 Cargo feature 决定**。
  我在把项目改造成 workspace 结构、重写 `Cargo.toml` 时，**把脚手架原本的 `[features]` 段删掉了**。
- **修法**：加回 feature，构建时带上它：

  ```toml
  [features]
  custom-protocol = ["tauri/custom-protocol"]
  ```

  ```powershell
  cargo build --release -p app --features custom-protocol
  # 或者更省心：pnpm tauri build（CLI 会自动加）
  ```

- **代价与教训**：
  - 我为此白跑了两轮 **28 分钟**的 release 构建。
  - **"没有报错"不等于"配置正确"** —— 该失败的链接没失败，
    只是安静地去连了一个不存在的开发服务器。
  - **不要用 `cargo build --release` 代替 `tauri build`。**
    Tauri 的生产构建不只看 profile，还看 feature。
  - 排查"窗口没有内容"这类问题时，**优先从 Rust 侧取证**（窗口数 / URL / eval 注入），
    比在前端猜快一个数量级。
  - 省时间的技巧：用环境变量覆盖 profile 做快速构建
    （`CARGO_PROFILE_RELEASE_LTO=false` 等）能把 28 分钟压到几分钟，
    适合"先验证再出正式包"。

### D21 · 三个 Live Photo 体验缺陷（用户实测反馈）

**① 大图里"播放的画面和照片不一致"** —— 真 bug，根因是**缓存映射没跟着视图清空**。

`screenKeys` / `screenCached` 都是**按"视图 id"索引**的（id → 缓存键）。切换侧栏目录后
id 会重新编号指向完全不同的照片，而我在 `reloadAssets()` 里清了 `assets`、`ready`、
`mounted`、`mountedHeads`，**唯独漏了这两个**。于是打开大图时会用一个属于**上一批照片**的
键去取清晰图 —— 显示的是 A 的照片，播的是 B 的视频（也就是用户看到的"不一致"）。

修法：`reloadAssets()` 里一并 `clear()`。

**② 必须长按才能播完** —— 原本是"按下播、松开停"（我照搬了 iOS 的按住手感），
但用户要的是**点一下播放、再点一下停止**。已改，并**去掉松开即停**。

**③ 切过去自动播放** —— 对齐 iOS 相册：滑到 Live Photo 就自动播一遍。
在 `openViewer` 里延迟一拍调用 `playLive()`（等缓存键的异步流程走完，避免打架）。

顺带修掉一个我写错的默认值：静音偏好原本写成
`localStorage.getItem(...) !== "0"`，于是"没存过偏好"也被判为静音
（`null !== "0"` 为真）——**自动播放全程没声音**。正确的是 `=== "1"`，默认**有声**。
另外给查看器加了静音开关，偏好持久化。

**④ 小图模式悬停播放"先黑一下"** —— `#hoverVid` 的 CSS 写着 `background: #000`，
而我在**视频解出第一帧之前就把元素显示了出来**，于是先看到一块纯黑。三条一起修：
- 背景改 `transparent`（底下的缩略图能透出来）
- 不用 `display:none` 隐藏（那样浏览器可能不解码首帧），改成常驻 + `opacity: 0`
- **以 `loadeddata` 为闸门**，首帧就绪后才加 `.shown` 淡入

> **易漏点**：`screenKeys` 这类"按视图下标索引的旁路状态"必须与 `assets` 同生命周期。
> 以后凡是新增这类映射，都要在 `reloadAssets()` 里一起清。

### D22 · 工作池接口重构：把"提交"和"声明需要"合并成一个入口

D18 的四处缺陷是**同一个根因**：任务在取出执行前会检查"这个键现在还需要吗"，
不需要就丢掉，而这个检查依赖调用方**另外**记得调用 `set_wanted` / `pin`。
忘了不会报错，只会静默丢任务（实测：胶片条请求计数涨到 297、零产出）。

修法不是"再补一次文档提醒"，而是让错误**写不出来**：

```rust
pub enum Keep { Wanted, Pinned }          // 保活方式
pub fn request(&self, reqs: Vec<ThumbRequest>, keep: Keep)   // 唯一入口
```

- `Keep::Pinned` 在 `request()` 内部就把键放进 `pinned`，"提交即声明"，
  调用方再也不可能只提交不声明；
- `Keep::Wanted` 对应网格可见窗口 —— 它本来就要配 `set_wanted`（该方法会**整体替换**集合），
  顺序也被写死：先 `set_wanted` 再 `request`，反过来刚入队的任务会被立刻裁掉。
- 原来的 `submit()` 已删除，全仓库再也搜不到不带 `keep` 的提交点。

四个调用点：`set_visible`（Wanted）、`request_screens`（Pinned）、
`request_grid`（Pinned）、`request_screen`（Pinned）。
其中 `request_screens` / `request_grid` 原本手工维护"哪些旧键该解绑"的循环保留，
但"新键要 pin"那段删掉了 —— 那正是会漏的地方。

### D23 · "有些视频点开直接卡死"：读盘发生在 UI 线程上（2.08GB 文件实测）

用户的反馈只有一句"有些视频文件点开直接卡死"。查下去发现**两件事叠在一起**：

**① 协议处理器是同步的，所以读盘发生在主线程。**
Tauri 的 `register_uri_scheme_protocol` 最终由 wry 在 WebView2 的
`add_WebResourceRequested` 回调里**同步**执行（wry 0.55 `webview2/mod.rs`：
handler 返回的响应就地 `SetResponse`）。也就是说 `serve_media` 里那句
`f.read_exact(&mut buf)` 是在 UI 线程上跑的。

**② 播放器第一个请求是开放式范围（`Range: bytes=0-`），旧代码没有上限。**
用户库里最大的一个视频是 **2.08 GB**（4K、325 秒）。于是：主线程要分配并读取
2.08GB，再拷贝进响应体。实测宿主进程私有内存 100 秒内从 **10MB 涨到 4277MB**，
应用停止响应（更早的两次尝试里进程直接被终止，退出码 `0xE0000008`）。

修法两道防线，缺一不可：

1. **单次分片上限 4MB**（`LIVEPHOTO_MEDIA_CHUNK` 可覆盖，`0` = 关闭）：
   返回 206 + `Content-Range`，播放器会自己继续请求下一片 —— 这是媒体服务器的正常路径。
2. **注册异步协议 + 专用 IO 线程池**（`register_asynchronous_uri_scheme_protocol`
   + `IoPool`）：读盘彻底离开 UI 线程。

修完的实测（`tools/video-sweep.ps1`，同一台机器、同一批文件、同一份前端）：

| 指标 | 旧行为（同步 + 不限分片） | 现在（异步 + 4MB 分片） |
|---|---|---|
| 2.08GB 视频 | 主线程被堵死，进程终止（`0xE0000008`） | `canplay` 274ms，**主线程停顿 0ms** |
| 宿主进程私有内存峰值 | **4277 MB** | **28 MB** |
| 单文件经协议实际传输 | 整个文件（2.08GB） | 16–29 MB（播放器只要头部+起始样本） |
| 单次读盘最慢 | —（一次读 2.08GB） | 44 ms |
| 16 个大文件（最大 2.08GB） | — | **16/16 `canplay`、0 失败、最差停顿 0ms** |

> 复现方式（同二进制 A/B，只切环境变量）：
> `pwsh tools/video-sweep.ps1 -Legacy` 与 `pwsh tools/video-sweep.ps1`。
> 前端自检会把每个文件的结论**每测完一个就写一次盘**，
> 所以即使进程真的被搞死，最后落盘的 JSON 也精确指出了是哪个文件。

### D24 · 播放不能被缩略图堵住：IO 池改成"媒体优先"双队列

有 4 次运行里出现 1 次异常：首屏正在加载（918 个视频资产要靠 MF 抽帧）时，
`mediaTest` 6 秒都没到 `canplay`，同一份 1.965s 的 MOV 在首屏安静时只要 274ms。
我**没有**把这个现象完全归因清楚（也可能是 GPU/CPU 争用），
但有一个结构性隐患是确定的：缩略图请求与播放请求当时**共用一条先进先出队列**，
首屏成百上千个缩略图请求会让播放排在它们后面。

所以 `IoPool` 改成同一把锁下的两个队列，取任务时**先扫媒体队列**，
并加了 `behindThumbMax` 计数（媒体请求到达时缩略图队列里还压着多少个）用于取证。
改完连跑 4 次首屏：`canPlay=true`、`readyState=4`、`livePlays=1` 全绿
（`tools/boot-selftest.ps1 -Runs 4`）。

> **诚实的边界**：这是"把确定的结构性隐患消掉 + 4 次复测通过"，
> 不是"已证明那个偶发失败的唯一根因"。文档里保留原始失败记录，不做删除。

### D25 · 放大后点一下就退回小图：`setPointerCapture` 会改写 click 的 target

用户反馈：大图放大后鼠标点一下直接退回网格。

根因不是"关闭按钮太灵敏"，而是**事件目标被 WebView2 改写了**：
放大状态下 `pointerdown` 会 `setPointerCapture(vStage)`，
于是随后的 `click` 事件的 `target` **总是 `vStage`** ——
"点在照片上"和"点到底背景"在事件里**完全无法区分**，
而旧逻辑看到 `target === vStage` 就 `closeViewer()`。

修法是把判断从"事件目标"换成"几何命中"：

```ts
function pointInsideImage(clientX, clientY) {
  // 用 fitBox + 平移/缩放算出大图当前在屏幕上的矩形
}
// click 时：点在矩形内就不关；只有真点在照片外的空白处才关
```

另外把"拖拽后抑制 click"改成**只有真的移动过（≥3px）才抑制** ——
原来只要按一下就抑制，等于"放大后点一下什么都不会发生"。
合成事件下 `setPointerCapture` 会抛异常（没有活动指针），也补了 try/catch。

自检把它变成可复现的数字（`ui-viewer-selftest.json`）：
放大状态点照片内部 → 查看器仍在（`stayedAfterImageClick: true`）；
复位后点舞台角落 → 查看器关闭（`closedOnBackdropClick: true`）；`pass: true`。

| # | 坑 | 症状 | 教训 |
|---|---|---|---|
| K1 | MOV box 解析偏移按"box 起点"算，实际拿到的是"体起点" | 视频轨识别不出来（codec/宽高全空）；时长解析成 256000ms（真值 1940ms） | 这类差 8 字节的 bug **不会报错**，必须拿已知真值对账 |

| K7 | 用 PowerShell 的 `-replace`+`Set-Content` 改源码 | 文件被写成非 UTF-8，读都读不了（PS 5.1 按 ANSI 读写 UTF-8） | **不用 shell 编辑源文件** |
| K8 | 把"内容构成变化"当成"性能退化" | 看到吞吐从 8/s 掉到 4/s，误判为"越跑越慢"，还写进了文档 | **性能结论必须带上内容构成一起看**（已撤回该结论） |
| K9 | debug 版 Tauri 加载 `devUrl` 而非内嵌 `dist` | Vite 一死窗口就全白、且**没有任何报错** | 验收要固化脚本；release 构建可消除这个脆弱性 |
| K10 | **只 `submit` 不声明"我要它"** | 任务被工作线程静默丢弃：`request_grid` 的计数一直涨（297 次）却永远不出图；表现为"网格能加载、胶片条不行" | 池子的守卫是"不在 wanted∪pinned 里就跳过"——任何绕过 `set_visible` 的提交路径都必须同时 `pin` |
| K11 | **`cargo build --release` 不等于生产构建** | release 二进制仍加载 `devUrl`：窗口白屏、无任何报错、缓存零增长 | tauri 用 `let dev = !custom_protocol;` 判断，**必须带 `--features custom-protocol`** 或用 `pnpm tauri build` |
| K13 | **按视图下标索引的旁路状态没跟着视图清空** | 切目录后 `screenKeys` 仍指向旧照片的缓存键 → 大图显示 A 的照片、播放 B 的视频（"播放和照片不一致"） | 凡"按数组下标索引"的映射，必须与数组同生命周期；`reloadAssets()` 是唯一的清理点 |
| K14 | "默认值写反"型静音 bug | `!== "0"` 让"未设置"也判为静音，自动播放全程无声 | 布尔偏好用肯定式判断（`=== "1"`），并给它一个显式的默认值 |
| K12 | 用 PowerShell 的 `-replace`+`Set-Content` 批量改源码 | 见 K7；同类问题的另一面是"把脚手架的 `[features]` 段整个删掉"也会安静地毁掉生产构建 | 改结构时逐段核对，别整段重写配置 |
| K15 | **以为自定义协议处理器在别的线程上跑** | 在处理器里读文件 = **在 UI 线程上读文件**（wry 在 WebView2 的 `WebResourceRequested` 回调里同步执行 handler）。一个 2.08GB 的视频被整段读进内存，界面直接卡死 | Tauri 的同步自定义协议 = **UI 线程上的同步代码**；重活要么走 `register_asynchronous_uri_scheme_protocol`，要么别做 |
| K16 | **忘了 `setPointerCapture` 会改写后续 click 的 target** | 放大后点一下照片就退回网格：`pointerdown` 捕获指针后，click 的 `target` 恒为捕获元素，于是"点照片"和"点空白"在事件里长得一模一样 | 有指针捕获时，**用坐标做几何命中判断**，不要相信 `event.target` |
| K17 | 一次失败就当成"已修复" | 首屏播放超时 4 次里出现 1 次，同一二进制前后都通过 | 偶发问题必须**连跑多次给通过率**（`tools/boot-selftest.ps1 -Runs 4`），并保留那次失败记录 |

### 已知缺口（按优先级）

1. **安装包（MSI/NSIS）** —— 目前交付的是绿色版单文件 `LivePhotoBrowser.exe`，
   双击即用，但没有集成安装器与开始菜单项。
2. **剧照对齐** —— 要求"从剧照那一帧起播"，目前整段从 0 播；`still-image-time` 已解析出来，接上即可。
3. **偶发的一次播放超时未定位**（见 D24）—— 结构性隐患已消除、4 次复测全绿，
   但没有证明它就是那次失败的唯一根因。
4. **方向一致性** —— `<video>` 报 1440×1920（Chromium 应用了旋转矩阵），
   而 MOV 元数据解析出 1920×1440；从 MOV 抽帧那条路要注意旋转未被应用。
5. **日期用文件 mtime 而非 EXIF 拍摄时间** —— 需要解析 HEIC 的 EXIF。
6. **滚动没有惯性** —— D8 自己接管滚轮的代价。
7. **磁盘占用** —— 1024 网格层 + 2048 全屏层，1 万张合计约 9GB（有 4GB 上限兜底，
   但会频繁触发淘汰、反复重算）。建议"全屏层不落盘"，它本质只是当前这张的临时产物。
