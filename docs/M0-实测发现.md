> 环境：Windows 11 22631，8 核，Intel Iris Xe 集显，本地控制台会话（非远程），
> 已装 HEIF/HEVC 扩展，release 构建（除注明外）。

## M0-4 · WebView2 虚拟化网格滚动（先看好消息）

命令：

```powershell
# 需要先起 Vite（debug 构建的 Tauri 会加载 devUrl 而不是内嵌 dist）
cd app; pnpm dev
.\target\debug\app.exe          # 页面自动跑基准并把结果写盘
```

结果：`m0-results/grid-scroll-bench.json`

环境：窗口 1440×900，DPR **2.25**，WebView2 = Edge/Chromium 152，300 张真实 512px JPEG 循环填充 5000 格。

| 场景 | fps | p50 | p95 | p99 | max | >50ms | 长任务 | DOM 节点 |
|---|---|---|---|---|---|---|---|---|
| empty（纯占位块） | 58.1 | 16.7ms | 16.9ms | 32.9ms | 133.3ms | 2 | 0 | 88 |
| **images（真实 JPEG）** | **58.5** | **16.7ms** | 16.9ms | 33.5ms | 50.1ms | 2 | 0 | 88 |

**解读**：
- p50 恰好等于 16.7ms = 60Hz 的帧预算，说明滚动**跑在 vsync 上、没有额外开销**，
  已经是这块屏的物理上限（本机不是 120Hz 屏，120Hz 目标无法在此验证）。
- **5000 格的 DOM 只有 88 个节点** —— 虚拟化有效，符合"10 万张也能滚"的设计预期。
- 97 帧里有 207 帧 >16.7ms，但 p95 只有 16.9ms，即绝大多数帧**刚好**贴在 vsync 上，
  1~2 帧的 50ms+/133ms 抖动出现在场景开头（首帧建图与布局），不是持续卡顿。
- 挂真实图片（含解码+纹理上传）后帧率与空场景**没有差别**，说明图片加载不是瓶颈。

→ **§4.3 的渲染方案（DOM 虚拟化 + transform 位移 + contain:strict）得到实测支持。**

### 踩到的坑（对 M1 很重要）

1. **debug 构建的 Tauri 加载 `devUrl`，不加载内嵌 `dist`。**
   直接运行 `target\debug\app.exe` 而没起 Vite，会得到一个白窗口、
   JS 完全不执行、也没有任何报错 —— 排查了很久。M1 起必须固化一套
   "一键起 dev / 一键跑 release 验收" 的脚本。
2. **绝不能在 Tauri 主线程初始化 MTA COM。** tao 创建窗口时会调 `OleInitialize`
   （要求 STA），主线程若已被改成 MTA 会直接 panic：
   `OleInitialize failed! Result was: RPC_E_CHANGED_MODE`。
   所有解码初始化必须放在工作线程（`media::worker_init`）。

## M0-1 · HEIC 解码管线

命令：

```powershell
.\target\release\bench_heic.exe "F:\DCIM" 40              # 主实验
.\target\release\bench_heic.exe "F:\DCIM" 40 jpg          # 控制实验
.\target\release\bench_heic.exe "F:\DCIM" 24 heic,heif nomf  # 对照：不调 MFStartup
```

### 主实验结果（40 张 iPhone HEIC，3024×4032，共 106MB）

| 场景 | p50 | p90 | min | max |
|---|---|---|---|---|
| A0 只创建解码器（不解像素） | 9.3 ms | 13.9 ms | 4.1 ms | **154.9 ms** |
| A 全尺寸解码（RGBA） | **434.9 ms** | 661.9 ms | 197.6 ms | **1691.1 ms** |
| B 解码 → 缩到 512px → JPEG q82 | **462.6 ms** | 697.1 ms | 198.6 ms | 1317.4 ms |
| C 全尺寸解码 → Lanczos3 → JPEG | 480.3 ms | 819.5 ms | 211.2 ms | 1710.9 ms |

- 512px JPEG 平均 **56.7 KB** → 1 万张缩略图 ≈ **553 MB** 磁盘缓存
- 缩放+编码只占 28ms（B−A），**瓶颈完全在解码本身**
- 6 工作线程并行：**3.01 张/秒**，等效 332ms/张（单线程 p50 462ms ≈ 2.16 张/秒）
- 推算 1 万张：单线程 **77 分钟**，6 线程 **55 分钟**

### 控制实验：同样的并行框架解 JPEG（4256×2832）

| 场景 | p50 |
|---|---|
| A0 只创建解码器 | **0.31 ms**（HEIC 是 9.3ms） |
| A 全尺寸解码 | 147.7 ms |
| B 解码 → 512px → JPEG | **118.3 ms** |
| 并行 6 线程 | **28.08 张/秒**，等效 35.6ms/张 → **提速 3.32×** |

→ **并行框架本身没问题**（JPEG 能到 3.3×）。**HEIC 的 1.4× 是解码路径本身的限制。**

### 对照实验：不调 `MFStartup`

| 场景 | 调 MF | 不调 MF |
|---|---|---|
| A0 创建解码器 | 9.3 ms | **307.5 ms** |
| A 全尺寸解码 | 434.9 ms | 892.7 ms |
| B 缩略图管线 | 462.6 ms | 879.6 ms |
| 并行吞吐 | 3.01 张/秒 | 2.68 张/秒（1.4×） |
| 1 万张推算 | 55 min | 62 min |

→ `MFStartup` 必须调（不调慢 2 倍），但**它并不是并行不加速的元凶**。

### 进程级实验：6 个进程同时各解 1 张 HEIC

| 方式 | 墙钟 |
|---|---|
| 逐个串行（6 次） | 9.43 s |
| 6 个进程同时 | 4.75 s |
| **加速比** | **1.99×** |

→ 连**跨进程**都只有 2×，说明瓶颈不是我们进程内的锁，而是**机器层面的共享资源/串行化**。

### 单张解码的资源画像

| 运行 | 墙钟 | CPU 时间 | 并行度 |
|---|---|---|---|
| 第 2 次 | 1.10 s | 0.58 s | **0.53** |
| 第 3 次 | 1.09 s | 0.58 s | **0.53** |

→ **接近一半时间在阻塞等待，而不是在算。** 这与"多线程/多进程都不加速"是一致的：
瓶颈是同步等待（跨套间/跨进程往返），不是 CPU 算力。

### 三个必须记住的技术结论

1. **HEIC 解码必须在 STA 套间里做，MTA 会永久死锁。**
   `CreateDecoderFromFilename` 在 MTA 下 30s+ 不返回、进程 0 CPU；
   同文件在 STA 下立刻成功。PowerShell 5.1（STA）用 WPF `BitmapDecoder`
   也能解出 4032×3024，交叉验证。原因：HEIF 解码器会回调调用方套间，
   只有 STA 的阻塞等待会顺带泵消息。
2. **`MFStartup` 必须调**（对 HEIC 解码有 2 倍收益）。
3. **`image` 的 JPEG 编码器不接受 RGBA8**
   （`The encoder or decoder for Jpeg does not support the color type Rgba8`），
   走 JPEG 的路径应直接让 WIC 输出 `24bppRGB`（`GUID_WICPixelFormat24bppRGB`）。

## M0-2 · Media Foundation 抽帧（Live Photo 的 HEVC 视频）

命令：

```powershell
.\target\release\bench_mf.exe "F:\DCIM" 6
```

结果：`m0-results/mf-frame.json`

样本：6 个 MOV，**HEVC**，1920×1440（2 个是 2816×1584），每段约 73 帧（≈2 秒）。

| 场景 | p50 | min | max |
|---|---|---|---|
| A probe（只读流信息） | 3.6 ms | 3.0 ms | 39.6 ms |
| B 首帧（原生 1920×1440 RGB32） | **222.3 ms** | 194.3 ms | **4417.4 ms** |
| C seek 到 1000ms（原生） | **239.6 ms** | 207.2 ms | 1204.6 ms |
| D seek 到 1000ms（缩到 256px） | **197.6 ms** | 153.4 ms | 228.3 ms |
| E 整段解码（2 段） | 3628 ms | — | — |

- 整段吞吐：147 帧 / 5.96s = **24.66 fps**（1440p，RGB32 输出含色彩转换与 CPU 回读）
- **D 只比 C 快 18%**：缩放到 256px 几乎不省时间
  → **≈200ms 主要是"每个 SourceReader 的一次性初始化"（解码器 MFT + 视频处理器建链），
  而不是像素工作量。**

### 对方案的影响

1. **抽单帧 ≈200ms，比 HEIC 的 462ms 快 2.3 倍** —— 对 Live Photo 来说，
   "海报帧优先从 MOV 取" 依然划算，但不是"毫秒级"，不能指望靠它撑起首屏。
2. **必须复用 SourceReader**：既然 200ms 主要是一次性初始化，
   那么按"一个 worker 一个常驻 reader"来做，连续抽帧的边际成本会大幅下降。
   M0 没有验证这一点，是 M1 的高优先级验证项。
3. **整段解码 24.66 fps 说明没有吃满硬件解码**（Iris Xe 解 1440p HEVC 应远高于此）。
   待查：换 NV12 输出（避免 RGB32 转换与回读）、显式配置 DXVA/D3D11 设备管理器。

### 踩到的坑

1. **`MF_SOURCE_READER_ENABLE_VIDEO_PROCESSING` 必须为真**，否则把输出类型
   设成 RGB32 会以 `MF_E_INVALIDMEDIATYPE (0xC00D36B4)` 失败
   （源是 NV12，需要视频处理器做转换）。我最初只在"要缩放"时才开这个开关，
   导致原生尺寸抽帧全部失败。
2. **4CC 不要用 `GUID::to_u128() & 0xffffffff` 取** —— 那取到的是 Data4 的尾巴，
   要用 `guid.data1.to_le_bytes()`。真实编码是 `HEVC`（不是容器里的 `hvc1`）。
3. `Lock`/`Lock2D` 必须成对 `Unlock`，否则缓冲区保持锁定。

## M1 前置实验 · 常驻 SourceReader 与输出格式（M0 之后追加）

命令：

```powershell
.\target\release\bench_mf_reuse.exe "F:\DCIM" 8
```

结果：`m0-results/mf-reuse.json`

### 可靠结论一：NV12 直出比 RGB32 快 3~4 倍（三次独立运行一致）

| 配置 | 第1次 | 第2次 | 第3次 |
|---|---|---|---|
| RGB32 native | 21.04 fps | 21.75 fps | 24.47 fps |
| **NV12 native** | **89.37 fps** | **85.24 fps** | **88.02 fps** |
| NV12 scaled 512 | 88.46 fps | 85.79 fps | 81.50 fps |
| RGB32 scaled 512 | 24.41 fps | 27.15 fps | 27.45 fps |

→ **瓶颈不是解码，是色彩转换 + CPU 回读。** NV12 下 1440p 每帧 ≈11ms，
30fps 实时播放只需 33ms/帧，**有 3 倍余量**。

→ 但**不要**因此认为"转 H.264 预览片段"这条降级路径可以取消：
本方案是 Tauri/WebView2 应用，**NV12 帧没法便宜地送进 WebView**
（要么转 H.264 交给 `<video>`，要么走原生叠加窗口，要么 GPU 转换后回读再经 IPC 推给
canvas——最后一条每帧 8MB，不可行）。所以：

- NV12 的收益体现在**解码那一段快了 4 倍**（转码时从 NV12 编码，而不是从 RGB32 编码）；
- 但"把画面送进 WebView"这一环**仍然需要**转码或原生渲染层，NV12 并不能省掉它；
- 对**抽海报帧**这条路径（要的是 JPEG 缩略图）需要额外一次 NV12→RGB 的转换，
  约 36ms/帧；即便如此仍优于直接 RGB32 抽帧（222ms vs ~100ms）。

这一条要等 M1 真正实现后实测，才能确定最终走哪条路。

### 可靠结论二：`ClipReader::open` 很便宜（p50 2.8~10ms，三次一致）

→ 我在 M0-2 里"≈200ms 主要是 source reader 建链开销"的**猜测是错的**。
200ms 出在首帧解码本身。**幸好量了没照着猜的写。**

### 可靠结论三：连续取帧的边际成本 p50 28.5~28.9ms（RGB32@512，三次一致）

### 不可靠：抽帧延迟与吞吐在多次运行间自相矛盾

| 指标 | 第2次运行 | 第3次运行 |
|---|---|---|
| 单张 NV12 首帧 p50 | 64.92 ms（→ 约 15 张/秒） | 67.32 ms |
| worker 扫描：1 worker | — | **1.04 s/张（0.96 张/秒）** |
| worker 扫描：6 workers | 5.8 张/秒 | 4.91 张/秒 |
| seek 到 1000ms | 1057.99 ms | 1050.65 ms |
| seek 到 1000ms（RGB32，另一组） | 83.6~110.9 ms | 同 |

**同一个操作（新建 reader + 取首帧）在不同位置测出 65ms 和 1040ms，差 16 倍。**
这不是噪声，是**资源生命周期问题**：每次 `ClipReader::open` 都会新建一套解码器/
硬件解码会话，而释放是异步的。长跑之后新会话可能在等旧会话释放，
于是"越跑越慢"，并且**加线程越多、单任务越慢**（6 workers 反而低于 1 worker 的有效吞吐）。

→ 这意味着 M1 必须专门处理"**解码资源的生命周期**"：复用常驻解码器、
显式释放、避免 open/close 抖动，并且**先建立稳定的基准**再谈优化。
→ 在这一点查清之前，**任何"滚到就有"的吞吐承诺都不可信**。

### 明确的不可能三角（供决策）

按目前已确认的数字推算：

| 路径 | 单张成本 | 吞吐 | 快速滚动所需 114 格/秒 |
|---|---|---|---|
| 热缓存（读磁盘 JPEG） | ~1ms | 远超需求 | ✅ **已实测 58.5fps 无掉帧** |
| Live Photo 走 MOV 取海报（NV12） | 65 ms | ~15 张/秒（单路） | ❌ 差 7 倍 |
| 普通 HEIC 解码 | 435~463 ms | ~2.2 张/秒 | ❌ 差 50 倍 |

→ **"滚到就有"在快速滚动下只能靠热缓存实现，无法靠解码速度实现。**
   所以"预热"不是可选项，而是这个体验目标的必要条件 —— 但可以做得无感：
   只预热你打开过的目录、后台低优先级、可暂停、并且优先预热你正在看的那一屏附近。

## M1-4 / M1-5 · 缩略图工作池、缓存与端到端跑通

### 端到端结果（真实 App，非 bench）

清空缓存后启动 App 自动打开 `F:\DCIM`：

|---|---|---|

### 被真实管线证伪的优化：MOV 海报快路径

`bench_mf_reuse` 里 NV12 首帧只要 65ms、RGB32 222ms，看起来比解 12MP HEIC（435ms）划算得多。
但放进工作池与剧照解码并行之后：

| 配置 | 吞吐 | 平均解码 | 最慢一帧 | 最慢/平均 |
|---|---|---|---|---|
| 1500 张，含 371 个视频任务，3 线程 | 3.79 张/秒 | 797 ms | 6097 ms | 7.65 |
| 同上 + 视频解码全局串行化 | 3.42 张/秒 | 745 ms | 8126 ms | **10.9** |
| **1500 张，仅剧照路径（默认）** | — | 224→385 ms | 325→3398 ms | 见下 |

算术核对：`371×3000ms + 1118×193ms = 平均 885ms`，与实测 745~797ms 吻合
→ **"抖动"全部来自视频抽帧这条路，它在池内约 3000ms/张，比独立测量慢 14 倍。**
→ 结论：**独立测出来的 6 倍优势在真实管线里不成立，所以默认关闭**
（`LIVEPHOTO_POSTER_FROM_VIDEO=1` 才启用），需要时再补一轮专门的测量。

### 更正：所谓"渐进退化"其实不存在，是**内容构成**造成的假象

我先前看到"跑久了越来越慢"（累计平均 224→385ms、最慢一帧 325→3398ms），
并把它当成"首次全库索引的主要风险"写进了本文档。**这个判断是错的，现予撤回。**

真正的原因是：**资产按拍摄时间倒序排列，而 HEIC/JPG 的耗时差 6.6 倍**，
于是后段桶里 HEIC 变多，看起来就像整体退化。

证据（把"每 100 张吞吐"与"该桶的扩展名构成"放在一起看）：

| 桶 | 张/秒 | 该桶内容构成 |
|---|---|---|
| 0-100 | 5.18 | jpg:100 |
| 100-200 | 5.54 | jpg:100 |
| 200-300 | 5.53 | jpg:100 |
| 300-400 | 6.54 | jpg:100 |
| 400-500 | 5.05 | jpg:70 tif:30 |
| 500-600 | 5.87 | jpg:100 |
| 600-700 | **3.06** | **jpg:73 heic:23 mov:3** |

唯一变慢的桶正好是唯一含 HEIC 的桶。

**判决性验证：按格式单独跑，曲线各自平坦。**

| 单跑（300 张 / 1 线程，512px JPEG q82） | 吞吐 | 平均 | 最慢 | 最慢/平均 | **退化比** |
|---|---|---|---|---|---|
| **HEIC only**（300 个 heic） | 1.12 张/秒 | **889 ms** | 2882 ms | 3.24 | **1.06**（平） |
| **JPG only**（300 个 jpg） | 7.39 张/秒 | **135 ms** | 224 ms | 1.66 | **0.86**（平） |

两个格式内部都**没有退化**（HEIC 分桶 1.33 → 1.25，JPG 分桶 6.88 → 7.98）。

### 更正后的真实瓶颈：HEIC 与 JPG 差 6.6 倍

| 格式 | 单张平均 | 单线程吞吐 | 缓存体积 |
|---|---|---|---|
| JPG（4256×2832 级） | **135 ms** | 7.4 张/秒 | 30.9 KB |
| HEIC（4032×3024 级） | **889 ms** | **1.12 张/秒** | 约 45 KB |

- HEIC 这里的 **889ms** 比 M0-1 单独测的 462ms（p50）更差。差异来自
  a) 这里是**均值**、分布长尾（最慢 2882ms）；b) 样本是库中"最新"的 300 张，
     机型/分辨率构成可能与 M0-1 那 40 张不同。**待用同一批文件复测以确认**。
- 这个差距无法靠加线程解决（已证实：HEIC 并行只有 1.4×）。

**对本机真实库的实际影响**（`F:\DCIM`：734 个 HEIC + 6,409 个 JPG）：

```
HEIC  734 × 0.889s ÷ 1.4 ≈ 466 s
JPG  6409 × 0.135s ÷ 1.4 ≈ 618 s
合计 ≈ 18 分钟（一次性，后台、可中断，之后全走缓存）
```

→ 结论：**一次性索引这个库约 18 分钟**，可以接受；之前的"2 小时"估算是被误判放大的。
→ 仍成立的部分：交互式浏览永远不被这个耗时阻塞（只解看到的那一屏，之后全命中缓存）。
→ 我为此加的"工作线程定期回收"（`LIVEPHOTO_RECYCLE`）在本次归因下**没有证据支持**，
   默认关闭保留，等有场景需要时再评估是否删除。

## M4-补 · "有些视频点开直接卡死"的测量与修复（D23 / D24）

用户只给了一句话，所以先用环境变量打开一次专门的取证自检，
让 exe 自己把每个视频的加载过程写成 JSON：

```powershell
$env:LIVEPHOTO_OPEN="F:\DCIM"
$env:LIVEPHOTO_SWEEP="16"          # 采样多少个视频（默认关闭，普通用户零开销）
pwsh tools/video-sweep.ps1         # 当前实现
pwsh tools/video-sweep.ps1 -Legacy # 老行为（同步协议 + 不限分片），同二进制 A/B
```

库里 7832 个资产里有 **918 个带视频**，最大的一个 **2.08 GB**（4K、325 秒）。

### 老行为：主线程读整个文件（复现成功）

| 采样时刻 | 宿主进程工作集 | 私有内存 |
|---|---|---|
| 10 s | 26 MB | 10 MB |
| 40 s | 2134 MB | **2143 MB** |
| 100 s | 1037 MB | **4277 MB** |
| 150 s | 667 MB | 4277 MB |

原因：播放器第一个请求是 `Range: bytes=0-`（开放式），旧代码没有上限 →
在**协议处理器里**（也就是 WebView2 的 UI 线程上）一次分配并读取 2.08GB。
另外两次 16 样本的运行里，进程被直接终止，退出码 `0xE0000008`。
这就是用户说的"点开直接卡死"。

### 现实现：异步协议 + 4MB 分片（同一批文件）

| id | 体积 | 结果 | 总耗时 | 主线程停顿 | 协议请求数 | 实际传输 | 单次读盘最慢 |
|---|---|---|---|---|---|---|---|
| 1263 | 2129.3 MB | canplay | 761 ms | **0 ms** | 8 | 28.6 MB | 27 ms |
| 714 | 1112.7 MB | canplay | 566 ms | 0 ms | 4 | 16.0 MB | 28 ms |
| 3296 | 931.5 MB | canplay | 546 ms | 0 ms | 6 | 20.8 MB | 28 ms |
| … | 887–930 MB ×6 | canplay | 581–789 ms | 0 ms | 5–9 | 16–28 MB | 35 ms |
| 661/4039/1371 | 3.7–6.0 MB（Live） | canplay | 531–760 ms | 0 ms | 3 | 4.4–7.0 MB | 35 ms |

**16/16 全部 `canplay`、0 失败、最差主线程停顿 0 ms**；宿主进程私有内存峰值 **28 MB**
（老行为 4277 MB）。关键点：一个 2.08GB 的文件，播放器开始播放**只需要 28.6MB**
—— 它要的是 moov + 起始样本，不是整个文件。老代码的"整文件读"从一开始就是纯浪费。
